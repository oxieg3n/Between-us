## Implemented source groups

The023 TypeScript projector imports the existing `financeView` and supplies `{role:"child",childId}` with the actual database `serverAt`. It does not calculate balances, parse matching effects or infer milestones from raw command kinds. Its minimal internal projection contains local date, scheduled/due/period key, and up to32 goal IDs with completion booleans. It carries no amounts, names, titles, activity or raw matching fields. The SQL boundary trusts only this server component, validates the bounded shape/date and CAS revision, and repeats child/family/contact authorization under locks.

Every raw matching action remains silent in013's transaction trigger, including configure, reveal, fund, reverse and reconcile. Such commands return before writing domain metadata, outbox rows, invalidations or shared quota counters. The023 scheduled projector may observe a completion only when the child's actual visible progress crosses100%; hidden funding/configuration whose child projection is unchanged cannot alter threshold markers, notification metadata or shared quotas. Revealing an already funded contribution can legitimately change that visible progress. A revision change alone never creates, cancels or suppresses a signal.

## Authority, privacy and transport

`app_private.domain_notification_events` stores bounded source identity, kind, actor/recipient/contact and family/child binding, dates and cancellation. It contains no message, question, chore title, name, finance amount, report evidence, journal or draft text. No raw client access or publication is added. Only a source transaction may enqueue through the private helper; neither clients nor the service role receive direct helper execution or policy/table writes.

Creation and current dispatch/receipt authorization require both usable identities and a current independently verified, accepted, approved contact with no block in either direction. Finance additionally requires the current child binding/consent and a current guardian in that child's family. Check-ins recheck the current schedule revision/creator/contact, current child membership/consent, today's date and open disposition. The recipient must still own the device and its active managed session and opt into notifications. Revocation, withdrawal, a closed identity, opt-out, expired session/device or block denies later authorization. Source creation adds no new family/pair locks after a finance transaction's family lock; contact and check-in sources already hold their authority locks.

Existing `notification_outbox` now has exactly one message or domain source. Existing dispatch and receipt RPC names, signatures and DTOs stay the same. Shared source locking snapshots the whole bounded batch, locks the union of all involved families in UUID order, then every relationship in stable pair order, before any outbox/receipt row lock. This preserves the 012 lock-order fix for mixed message/domain batches. Single-job authorization, ticket recording and completion use the same source helper.

The provider payload remains exactly neutral title/body plus `{invalidationId: UUID}`. It contains no domain kind, source/family/child/actor ID, amount or source text. An invalidation is a hint to open the app and fetch currently authorized data, never evidence of delivery/read. No category-specific title, deep link to private content, skip reminder or automatic message sending was added. The existing worker performs current authorization immediately before transport; authorization cannot retract a neutral request already handed to an external provider.

Existing private preferences, quiet-hour lease deferral, three-device limit, shared 500/hour global and 20/hour recipient/device-attempt quotas remain. Domain events expire for transport after 24 hours, check-in authorization additionally ends with its local date, dispatch uses at most five attempts and receipts at most eight within 24 hours.013 event sources do not backfill or notify when policy is off, and an existing occurrence is never reissued when settings later change.023 preserves eligible but unqueued financial transitions for a later current-projection check; nothing records successful delivery on quota exhaustion.

## Service scheduling contracts

`api.produce_due_checkins(p_limit int default 20) -> {status,created,sent:false}` is service-only, bounded 1–20. It uses database time and each reviewed schedule's timezone, selects only due authorized schedules without today's occurrence, prelocks the family/contact union, then rechecks before insertion. It returns aggregate counts only to the trusted service; no guardian gets child dispositions. Both global push delivery and `domain_notification_policy.checkins_enabled` must be enabled. A root-owned scheduler must call it serially in bounded repeated batches, then use the existing notification worker. No cron registration, public endpoint or cloud scheduler was created.

`app_private.domain_notification_policy` has four independently default-false fields: `contacts_enabled`, `checkins_enabled`, `chores_enabled`, `payouts_enabled`. Existing `communication_policy.push_delivery_enabled` is also required. Only reviewed owner migration/operations may change them; normal operators and family administrators have no policy API. A source event whose recipient has no opted-in current device produces no event/outbox, and later device enrollment does not replay old actions.

## Projected finance worker integration (023)

`createFinanceNotifications({serviceClient,enabled:false})` defaults to no producer RPC or HTTP. Root must explicitly enable the trusted component **and** approve `payout_reminders_enabled` / `savings_milestones_enabled` plus the existing push policy. The new helper registers no job, timer, provider or public API. Required integration ports are:

1. Call `financeNotifications.produce({limit:20,afterChildId?,childId?})` serially before dispatch. It reads at most20 private child scopes, loads each4-MiB-bounded aggregate snapshot, projects at DB time and CAS-queues at most20 domain events in total. Scope/dispatch limits remain1–20; the financial event budget is `max(8,limit)` so a one-scope run cannot starve a child with eight guardians. The SQL queue requires an explicit8–20 budget. A private revision or local-day race reloads/reprojects at most four times. Return shape is `{status,checked,created,nextAfterChildId,sent:false}`. Keep the UUID cursor server-only; the scheduler must advance it between batches and wrap to null, including across one-shot process restarts, so families beyond the first batch are visited. Do not log the cursor or expose aggregate state/revision through mobile or operational summaries.
2. Pass `financeNotifications.serviceClient` to the **existing** notification worker for both dispatch and receipt polling. This wrapper freshly projects new financial sources immediately before authorization and retries private CAS races. Other source kinds delegate unchanged. Ordinary `api.authorize_notification` / `authorize_notification_receipt` deliberately deny new financial sources without this projector path; merely enabling policies cannot bypass current financial eligibility. Four private conflicts return a storage error rather than falsely suppressing a job due to hidden activity.
3. Optional prompt integration after a successful finance command: invoke the same producer for `{childId}` **after** the authoritative commit.013's `finance_commands` insert trigger fires before the aggregate update, so it must not project a supposed new balance. Scheduled scanning works without this hook, but a new goal completed between its first two scans may be silently baselined; the post-commit hook avoids that timing gap. Worker enablement and cursor ownership remain Root integration gates before any delivery claim.

The existing `notification-cycle.ts` now wires the producer and wrapped client in source. Its pure cycle accepts optional `financeCursor:{read,write}` ports after operational approval; otherwise its cursor is memory-only for that instance. The local one-shot CLI persists the cursor under ignored `.local/notification-finance-cursor.json`, never stdout. It uses an exclusive own lock and a flushed temporary file/rename. Missing cursor starts at null; oversized, malformed or non-file cursor data fails closed without resetting it. A stale/foreign lock is not removed automatically and needs owner review. No post-commit finance hook was added: this worker deliberately uses observed completion transitions and does not promise capture between scans.

Service-only RPCs are `finance_notification_scopes(limit,after_child_id,child_id)`, `finance_notification_snapshot(family_id,child_id)`, `queue_finance_notifications(family_id,child_id,expected_revision,projection,limit)`, `finance_notification_delivery_snapshot(outbox_id,lease_token,receipt)` and `authorize_finance_notification(outbox_id,lease_token,receipt,expected_revision,projection)`. These take trusted service credentials; authenticated users cannot supply projections or fetch raw snapshots. Existing transport DTOs/payloads stay unchanged.

Before queueing, each transaction prelocks the current guardian/contact family union, then pairs, and checks the aggregate CAS and current child identity/consent. At delivery/receipt lookup, the wrapper obtains a new current snapshot and the final SQL authorization repeats the lease, family/contact, device session, private preference, current local date and current due/completion checks. Paid/held payouts and corrected/cancelled goals deny stale signals. Authorization cannot retract a neutral request already handed to the provider. New signals inherit the same quiet hours, finite retries,24-hour expiry, global/device quotas and neutral invalidation payload.

An observation stores only up to32 once-only goal completion markers and a bounded current payout latch/period, not ledger bodies or raw revision counts. First observation of a complete goal is a silent historical baseline; its consumed marker is not delivery evidence. For a newly eligible transition, payout processing reserves the entire current opted-in guardian/device target set (at most eight) before any goal consumes the budget. The whole payout source, outboxes and quota writes roll back if any target lacks a durable event with an outbox; a partial fanout never latches the child. Only successful full source creation updates payout latch/period.

Goal transitions update `announced` only after a durable source/outbox exists. Exhausted batch/quota capacity or unavailable device/contact authority leaves `complete:true,announced:false` for a later scan, with no new neutral notification yet. Retry must still find the goal complete and currently authorized; correction/cancellation denies stale transport. Initial historical baselines remain silent, and already queued/consumed goals never repeat. There are no quarter-progress streaks or repeated carried-debt reminders. This is current-state notification behavior, not guaranteed event capture or delivery.

## Export, deletion and retention

The existing own export core is wrapped to add `domainNotifications` containing only that requester's **received** metadata `{id,kind,createdAt,expiresAt}`. It excludes source references/counts, peer/actor IDs, credentials/device tokens and sent child check-in metadata. More than 1,000 metadata rows or a combined core over 7 MiB raises the existing capacity-review path before an artifact can claim readiness. Child finance still goes through the existing server projector; this wrapper never adds raw financial history or matching.

The existing staged deletion executor triggers domain cleanup only at `access_revoked`: cancel actor/recipient transport, erase its outboxes, erase unheld shared metadata, and retain cancelled metadata where either participant has the relevant finite hold. It appends accurate executed stages and preserves the existing generic public blockers and `deletionComplete:false`. It does not erase immutable finance history, provider copies, backups, identity references or local writing.

023 treats its signal descriptors as financial metadata under the same finite finance/identity/message holds. Removing the last corresponding domain event also removes that private descriptor. Own received `domainNotifications` retains its four-field projection. A separate subject-only `financeNotificationObservations` export field adds at most32 own records `{familyId,childId,goals:[{goalId,complete,announced}],payoutLatched,lastPayoutPeriod}`; goal lists are bounded to32. A guardian's own export contains no child's observations, and the existing fresh-reauthenticated requester=subject artifact gate still denies a guardian fetching a child's export. Combined cores remain bounded to7MiB before readiness. These fields contain no journal, hidden match, monetary amount or other author's checkpoints, and `announced` never proves delivery.

Access-revoked deletion erases unheld own threshold observations; a closed account's held observation can be erased by the existing bounded domain retention worker after holds expire. Even with no old events, retention precomputes observation plus retained subject membership/child families into the global family union **before any pair lock**, then rechecks finance/identity holds inside its observation DELETE. Actual hold creation shares those retained family bindings. A future hard purge/rebind must preserve that synchronization invariant. Active-account once-only markers stay bounded to the existing32-goal finance capacity so retention cannot make an old goal generate repeated congratulations.

`api.run_domain_notification_retention(p_subject_id uuid,p_operator_id uuid,p_limit int default 20) -> {deleted,allDataDeleted:false}` requires the existing independent privacy operator, reviewed local/hosted privacy execution policy and retention enablement. It snapshots up to 20 old events using the existing notification-retention days, prelocks all families/pairs, rechecks both participants' message/identity holds and finance holds where applicable, then deletes actual metadata/outboxes/receipts. This is separate from the existing receipt purge and privacy retention workers. The root must schedule/retry all required workers; none was enabled here.
