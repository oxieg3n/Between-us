# Privacy lifecycle implementation contract

2026-11-16. The root has applied migration `202611160004_privacy_lifecycle.sql`; its SQL/pgTAP outcomes belong in the root's test ledger. This document describes implemented contracts, not legal approval or permission to collect real children's information. No earlier migration was changed by the lifecycle helper. The root separately fixes/tests the nullable authorization issue in the applied communication case readers.

The owner requires guardian-managed setup **with** the child/teen for every child/teen account, at every supported age. A distinct child Auth identity, their own credential and acceptance, independent teen consent where required, and no ordinary guardian impersonation remain invariants. Minimum/maximum ages and state eligibility remain closed pending review; maximum reviewed US coverage and the youngest appropriate age remain the goal. Coarse guardian-declared state is the proposed jurisdiction signal, not GPS. See [child privacy requirements](CHILD_PRIVACY_COMPLIANCE.md).

## Identity and fresh authentication

`app_private.privacy_identity_actor()` validates the signed-request UID, JWT expiry, current managed Auth session/user binding, session expiry, deleted/banned state, confirmed email or enrolled child alias, and an existing parent/child profile in `active/closed` state. It intentionally does **not** require current family membership or child consent. Suspended profiles, expired/revoked sessions and onboarding/pending profiles still fail. Closed profiles can use an independently authenticated new session only for these privacy/status surfaces; closing a profile does not claim the Auth user is purged.

This helper is private. It is called only by own case-status, own privacy-job and own export/deletion requests. It does not replace or modify `actor()`, `account_usable`, finance, chat or contact authorization. A withdrawn child therefore cannot send/fetch messages or operate the ledger, but can check the status of a case they previously submitted. Public/offline safety information and seeking another safe adult remain available without enrollment or guardian approval.

Service-only `record_privacy_reauthentication(p_user_id uuid,p_session_id uuid,p_method text,p_auth_event_ref text) -> {id,expiresAt}` records a **five-minute, old-session-bound** attestation. The trusted root handler must verify the bearer against managed Auth, perform real credential reauthentication using an isolated Auth client, verify matching UID/email and required MFA, then bind the resulting managed event/session reference to the original session. Revoke that ephemeral new session. Never accept a client `reauthenticated` flag, client timestamp, arbitrary user/session pair or a normal refresh as proof. SQL independently checks the original session/user and database time; it cannot prove that a service caller actually checked the credential.

Allowed method strings are `managed_password`, `managed_password_totp`, and local-only `synthetic_fixture`. Reviewed method array defaults empty. `synthetic_fixture` additionally requires both explicit privacy fixture policy and identity `local_synthetic`; ordinary domains cannot use the local execution path. The reference is opaque and bounded to 200 characters; no password, nonce, bearer JWT, TOTP code or private content belongs in it or logs. Existing verified MFA must not be silently downgraded to password-only. HTTP reauthentication and native credential UX belong to the root integration; these SQL files do not implement a custom identity system.

## Own requests and case status

Authenticated RPCs:

| Signature | Behavior |
| --- | --- |
| `get_own_case_status(p_kind text,p_case_id uuid)` | Kind `report/privacy`; only `reporter_id/requester_id = current UID`. Returns `{id,kind,status,response,createdAt}`. No body/evidence or operator assignment. Guardian, reported person, other staff and guessed IDs receive the same denial. No fresh credential prompt needed for this narrow status check. |
| `request_own_export(p_client_id uuid)` | Requires fresh reauthentication and open reviewed execution policy; records self-only job. Three lifecycle requests/minute. Sender/client UUID replay is idempotent; changing export to deletion under the same identity is rejected. |
| `request_own_deletion(p_client_id uuid)` | Same protections. Creates a request, not a deletion claim or immediate account erasure. There is no subject/user/child ID parameter to target somebody else. |
| `get_own_privacy_job(p_job_id uuid)` | Requester only; returns status, completed stage names, public blockers and dates, `exportComplete`, `deletionComplete:false`, `journalIncluded:false`. No raw artifact, finance manifest/hash, reviewer metadata or confidential other-person case information. |
| `get_own_export(p_job_id uuid,p_allow_partial boolean default false)` | Requires fresh own reauthentication, self-only export and reviewed execution policy. Returns `{id,status,data,completed,blockers,journalIncluded:false}` only for an actual artifact. Partial retrieval requires explicit `true`; expiration erases stored artifact bytes and returns `data:null,completed:false`. A requested/approved unexecuted job raises `export not ready`. |

Jobs use `requested -> approved/rejected`, then `ready/partial_ready` for generated exports or `access_revoked/blocked` for deletion work. Export expiration is a separate `expired` state. Missing/expired worker reauthentication creates `blocked/fresh_reauthentication_required`; obtain fresh proof and submit a new logical request rather than replaying an old request as new authorization. Repeated worker execution is idempotent for already executed stages. A job is not complete because a request or review row exists.

## Independent operator execution

Only `service_role` may invoke the following. The trusted service must bind `p_operator_id` to the actual reviewing operator, not forward a client-selected identity under a privileged key. SQL checks active usable `privacy` scope, independence from requester/subject and their family guardians, current assignment where relevant, policy and bounded input. Ordinary parent/guardian status never grants this power.

- `review_privacy_job(p_job_id,p_operator_id,p_decision,p_reference)` approves/rejects an own-data request, recording opaque review evidence. Approval alone does not run the job.
- `execute_privacy_job(p_job_id,p_operator_id)` runs the assigned approved job while its original reauthentication remains fresh. Session locks precede family locks; families and relationships lock in deterministic order before job mutation. Last-guardian deletion with active dependent children blocks for a reviewed handoff instead of silently stranding them.
- `queue_parental_privacy_review(p_request_id,p_operator_id,p_reference)` converts a submitted `parental_review/guardian_dispute` record into an explicitly **blocked legal-review job**. It cannot be automatically approved/executed into another author's export/deletion. Parent rights, custody disputes, an unsafe guardian and device-only journal conflict require a separate lawful disposition; recording a request is not denying a valid statutory right or granting a key bypass.
- `get_privacy_job_review(p_job_id,p_operator_id)` exposes precise internal stage/blocker categories only to the assigned independent reviewer. It contains no report body or reported-person report listing.

All mutable authorization predicates fail closed on SQL NULL; assignment checks use `IS DISTINCT FROM`, explicit nonnull identity checks or positive/coalesced permissions. No raw table grant or Realtime publication is added.

## Export scope and child finance projection

The generated JSON artifact includes the subject's profile, own memberships/contact participation, their own block decisions, scoped consent status/notice data, own sent saved messages and previously **acknowledged** received messages, reports they themselves filed, privacy requests they themselves filed, own notification preferences and device metadata. It excludes bearer credentials, device tokens, raw verification evidence, another person's private block edge and reports made **about** the subject by another person. A guardian's own export never includes a child's confidential report or local writing. Undelivered received bodies cannot be recovered through export after a block or withdrawal.

There is no journal, private-draft, model session, key or cloud-journal data to export. Author-local journal export is a separate device capability. Limits: at most 1,000 visible own messages and 100 own reports/requests per snapshot; core <=7 MiB, completed artifact <=8 MiB. Exceeding capacity blocks for review instead of silently truncating. Artifacts live at most 24 hours in a private table and require fresh reauthentication to download. The HTTP/client layer must provide an explicit local download/preview and safe cleanup, not automatic email/cloud delivery. No filesystem export or provider storage was created here.

Parent financial exports now require the scoped parent-view process below; legacy raw own-command finance payloads are removed before an artifact becomes available. Child artifacts **never** contain raw ledger/events, revision/counts or hidden parent matching. Every child export enters `partial_ready/finance_projection_pending` regardless of whether there is hidden activity. Source manifests and hashes are service-only. To complete a child export:

1. `privacy_finance_sources(p_job_id uuid,p_operator_id uuid)` returns server-only `{childId,state,sourceHash,actor:{role:"child",childId},serverAt}`. Requires the assigned independent reviewer, own child subject, valid artifact and fresh original proof. Empty finance data produces an ordinary empty state rather than bypassing projection.
2. The trusted server invokes the **existing** `financeView(state,{role:"child",childId},childId,serverAt)` implementation; do not create a second arithmetic engine or accept a client projection. Do not substitute the parent actor or expose the source in an HTTP response/log.
3. `attach_privacy_finance_projection(p_job_id uuid,p_operator_id uuid,p_source_hash text,p_projection jsonb)` rechecks the source hash/current lock, own child ID, bounded view shape and prohibited raw/parent matching fields. Hidden parent event IDs cannot appear in the child view. Stale source returns service-only `status:conflict`; reread/reproject. Successful attach changes the artifact to `ready` with an explicit executed stage.

SQL validation is defense in depth; it cannot independently prove the financial arithmetic or every semantic omission in a privileged server's projection. Existing role-safe finance tests plus root integration/equivalent-world checks remain required. A source hash/revision or raw state must never be sent to the child. Snapshot components have their recorded build times; this is not a database-wide point-in-time backup.

| Service-only RPC | Signature and behavior |
| --- | --- |
| `privacy_parent_finance_sources` | `(p_job_id uuid,p_operator_id uuid) -> {id,status,actor:{role:'parent'},families:[{familyId,childIds,state}],sourceHash,serverAt}`. States appear once per family. Both RPCs validate the assigned independent privacy operator, own parent subject/requester, reviewed privacy execution policy, active managed parent account and live **original requested session**, unexpired artifact and original fresh step-up proof. Approved jobs must execute before sources/attachment are available. The service then invokes the existing `financeView(state,{role:'parent'},childId,serverAt)` once per required child and attaches one batch atomically. Parent raw state never becomes client artifact content; child projection RPCs and omission rules are unchanged.

Session locks precede the existing deterministic family/relationship locks, then the 011 administrator-admission lock and job row lock. Changed membership-family sets during lock acquisition abort for retry instead of acquiring a new lower family after a relationship lock. The admission lock serializes new guardian/family admission while the snapshot is built; family locks serialize financial mutation/child-scope revocation. Each source hash binds the complete ordered authorized-family states, scopes and review requirement. Attach recomputes it under locks and compares the saved source hash/manifest. Any changed state/scope returns service-only `conflict`; the worker rereads and recomputes the entire batch at most three times. Exact ready attachment replay is idempotent; changed replay is rejected.

Completion requires every eligible view attached from a consistent source batch and no scope-review blocker. Capacity is bounded to four families, 48 scopes, 6 MiB service source and an assembled 8 MiB artifact including the refreshed own check-in metadata. Oversized sources become `blocked/export_capacity_review_required`; oversized assembled artifacts stay explicitly `partial_ready/export_capacity_review_required` with no truncated batch attached. A former-scope review keeps `completed:false` even after all currently permitted views attach. The backend cannot make a smaller incomplete selection and label it complete.

`get_own_export` retains fresh own authentication and adds current parent authorization checks for every stored finance scope before retrieval. A later revoked guardian/closed scope cannot download the old ready financial artifact. Worker replay also strips its stale financial views and restages it for current-scope projection and independent review. An account/session that is no longer usable cannot obtain raw parent sources or complete/replay financial export. Completed artifacts remain dated snapshots; a subsequent ordinary ledger event alone does not revoke a still-authorized person's historical artifact. No new guardian access to child reports, private skips, journals or another family's data is granted.

Parent projection shape/recursive validation is defense in depth. A privileged projection service is still trusted to run the existing engine correctly; SQL does not prove every arithmetic result or infer all omitted financial semantics from arbitrary JSON. The 18 adapter tests include three-scope/two-family parent projection equality against the real engine, authorized matching presence, bounded CAS retries, malformed duplicate scope rejection, incomplete/capacity statuses and generic revocation denial. The earlier child hidden-match tests still pass.

## What staged deletion actually executes

Approved own deletion revokes contact/membership/consent authority, managed sessions and device tokens; erases neutral outbox/preferences/own invalidations/budget rows; expires issued enrollment/invitation authority; closes/redacts the profile/child label unless held; erases unshared, unacknowledged **own sent** messages when neither participant has a hold and no case references them; erases closed unheld reports the subject themselves filed; and erases their prior export artifacts. Idempotent replay cannot recreate authority or return deleted data.

It deliberately stops at `access_revoked`, with `deletionComplete:false`. It does not erase immutable shared finance history, acknowledged multiparty messages, another person's safety report, necessary identity/consent references, Auth identity/credential records, provider/backup copies or an offline journal. Holds may preserve bytes while still revoking access. The Auth user remains because current foreign keys and immutable ledger records need a reviewed purge/anonymization design. Reauthenticating a retained Auth identity never restores its closed profile's chat/finance rights.

The public blocker list is stable for every executed deletion: `shared_record_review`, `restricted_records_review`, `retention_review_required`, `auth_identity_purge_pending`, `provider_deletion_confirmation_pending`, `backup_expiry_confirmation_pending`, `local_device_erase_not_confirmed`. Its contents do not reveal whether another child has reported an alleged unsafe guardian. Precise internal blockers identify the remaining schema/provider/device work without exposing report evidence. There is no function that marks full deletion completed merely from an operator checkbox. Full deletion remains a release blocker, not a completed feature advertised to families.

## Finite retention and holds

Service-only `set_privacy_hold(p_subject_id,p_scope,p_reference,p_expires_at,p_operator_id)` creates an independent-reviewed finite hold, maximum one year, with review due within 30 days; `release_privacy_hold(p_hold_id,p_operator_id)` records release. Scopes: account/identity/consent/messages/reports/finance. Holds prevent relevant content erasure, not security revocation. Do not send a hold/case notification to an alleged unsafe person. Actual legal duties, safe notice and review staffing remain unapproved.

`run_privacy_retention(p_subject_id uuid,p_operator_id uuid,p_limit int default 100)` is service-only, independent-reviewed, policy-gated and bounded 1–100/category. It actually erases expired own artifacts, expired reauth receipts after one day, old budget rows, terminal neutral notifications (proposed seven days), old closed own reports/privacy requests (90 days), and unheld old messages (90 days) after respecting both participants' holds and case references. It writes an executed run with actual deletion counts available only to the trusted operator. The root must schedule/retry and test the worker; no timer/deployment was started.

These are proposed synthetic settings, not approved statutory periods. The runner explicitly reports outstanding immutable ledger, identity/consent/multiparty, provider/backup retention and hold-followthrough blockers. Unfinished jobs, consent receipts, registration/invitation/audit records and restricted other-person cases still require a complete approved lifecycle; this implementation does not claim that a narrow retention batch satisfies every record category. Backups need tombstone/restore verification and actual expiry evidence. No private device's erase can be confirmed remotely.

## Server adapter and bounded verification

`services/backend/src/privacy.ts` exports `createPrivacyService({url,publicKey,serviceClient})` for trusted server use. `PrivacyServiceError.code` is `not_authorized`, `invalid_request` or `temporarily_unavailable`; messages are fixed and never echo provider errors, credentials, report text or raw SQL.

`reauthenticate({authorization,password,totp?}) -> {expiresAt}` uses managed `getUser` and verified `getClaims` on the old bearer, an isolated non-persisting/non-refreshing `signInWithPassword`, and UID/email/session binding. It inspects existing and fresh verified factors; TOTP requires a fresh `challengeAndVerify` and verified `aal2` claims, even if the old JWT was already AAL2. Non-TOTP-only verified MFA fails closed in this adapter. For multiple verified TOTP factors it deterministically uses the first ordered factor; a reviewed factor-selection UX is not implemented here. The six-digit code is transient. Newly appearing verified MFA is checked again before password-only attestation.

Every new managed session is retired in `finally` using service `admin.signOut(token,'local')`, never global sign-out. Multiple JWTs for one MFA-upgraded temporary session are deduplicated by verified session ID, using the latest token. The original session is protected. Cleanup must succeed **before** the SQL attestation is written; cleanup failure returns unavailable and creates no successful proof. The managed Auth event reference is the retired temporary session's ID, not its bearer token. No session/credential persistence, callback logger or custom token validation is added.

`executeAndProject(jobId,operatorId)` is a service-worker method. It calls the reviewed SQL executor, then only for `partial_ready` loads the service-only source for its trusted SQL `projectionKind`. Child jobs invoke the existing `financeView` with an explicitly bound child actor; parent jobs project every permitted family/child scope as above. It reattaches by source hash and retries at most three source conflicts. It returns sanitized `{id,status,completed,journalIncluded:false,stagesExecuted?}`, never the source, revision, financial details or artifact. Deletion/blocked results cannot claim completed export/deletion or trigger a finance read.
