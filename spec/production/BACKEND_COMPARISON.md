# Backend comparison and decision

Reviewed: 2026-11-16. Status: **Supabase selected as the provisional local foundation; hosted evaluation and production remain gated.** This is an architecture recommendation, not a service connection, security certification or permission to collect real data. The current mobile prototype remains fictional and memory-only under [BOUNDARIES](../security/BOUNDARIES.md).

## Decision

Use one Supabase stack for the next isolated, synthetic-data backend spike: Auth, PostgreSQL, deny-by-default RLS, transactional database functions and, only after revocation tests, private Realtime invalidations. Run locally first; no cloud project, paid plan, account access or credentials are required for the decision. Supabase's local stack requires a compatible container runtime on Windows; local development is free and does not consume hosted quotas. Starting Docker and the stack is the integration owner's responsibility, not an already completed check. [Local development](https://supabase.com/docs/guides/local-development).

The deciding requirement is relational authorization plus atomic household finance: family membership, independently approved/accepted/verified contacts, blocks, command idempotency, immutable events and private child projections. PostgreSQL functions, constraints and locking give these one transaction boundary. This fit assessment is our inference from the documented capabilities, and must be demonstrated under concurrency rather than accepted from the provider name. [Database functions](https://supabase.com/docs/guides/database/functions), [PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html).

## Alternatives

| Stack | What fits | Work still owned by Between Us | Decision |
| --- | --- | --- | --- |
| Supabase Auth + PostgreSQL + Realtime | Integrated sessions, relational records, RLS and transactional functions; local equivalent for policy tests | Family/age/consent verification, recovery, narrow function grants, revocation, backups, abuse handling and production email | Preferred local foundation, conditional on the tests below |
| Cloudflare Workers + D1 + optional Durable Objects + managed OIDC identity | Small API and SQLite relational storage; D1 transactional batches; DO coordination/WebSockets | Choose/integrate consumer identity, validate tokens, write every authorization route/event, coordinate revocation and email; avoid splitting one financial transaction between D1 and DO | Viable if an API-centric team accepts that additional assembly; no need to add this layer to Supabase now |
| Firebase Auth + Firestore + FCM + Functions | Integrated mobile identity, document listeners and push transport; Firestore atomic transactions | Document/rule design for relational membership and hidden projections, authoritative finance service, listener/retry costs and function operations | Not preferred: hosted Functions requires Blaze billing, contrary to the present no-paid-plan constraint |

Cloudflare D1 `batch()` rolls back the sequence on statement failure: it is not accurate to reject D1 for lacking atomic batches. A Worker read, application decision and later separate write still need a correctly designed concurrency boundary. DO is optional coordination, not a second authoritative ledger. Cloudflare Access supports identity-provider integration; it does not supply the application's reviewed family/child relationship model. [D1 database API](https://developers.cloudflare.com/d1/worker-api/d1-database/), [Access identity FAQ](https://developers.cloudflare.com/cloudflare-one/faq/authentication-faq/).

Firestore supports atomic document transactions and retries on contention; transactions fail offline. The rejection is a fit/billing tradeoff, not a claim that Firestore cannot implement finance. FCM transport being no-cost does not make trusted sending, tokens, retries, receipts or authorization automatic. [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions), [Firebase pricing](https://firebase.google.com/pricing).

## Required design conditions

1. **No remote journal surface.** Do not create journal/draft/model-prompt tables, buckets, endpoints, realtime events or notification bodies. Local reflection remains on-device. Sharing is a separately composed, explicitly reviewed message. Family administrators have no journal authority. Future reviewed local storage is a separate decision.
2. **Authority comes from the session and current database state.** Derive account and family permissions server-side. Do not trust a client role, child ID or consent flag. Approval, invitation, acceptance and verification stay independent. Block/removal must win over queued sends and delivery. Safety information and confidential help remain available without guardian approval.
3. **No raw ledger client subscription.** Expose only authorized projections. Financial commands use integer minor units, database constraints and a single transaction with appropriate row locks; atomically cover the idempotency result, occurrence uniqueness, holds, source lots, monthly cap, compensating events and outbox. Restrict direct writes to authoritative tables. Child projections must preserve equivalent-world non-disclosure of surprise matching.
4. **RLS is necessary but insufficient.** Enable it on exposed tables; test unauthenticated and cross-family callers. Secret/service-role keys bypass RLS and never belong in Expo public variables or the mobile bundle. Views and privileged functions require explicit review; prefer invoker functions, or a tightly scoped definer with fixed search path, explicit actor checks and revoked default execute grants. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Function security](https://supabase.com/docs/guides/database/functions).
5. **Realtime revocation is a release blocker.** Supabase Broadcast/Presence policies are cached for the connection; a revoked member may continue receiving until JWT expiry or refresh. Use private per-account, content-free invalidations followed by an authorized fetch. Do not broadcast private bodies, financial values, matching activity or sensitive identifiers to membership-based shared topics. Reauthorize outbox delivery and avoid even timing/count disclosure to children. Dropping a client connection alone is not proof of server revocation. Prove the final design with an already-connected hostile client; otherwise keep Realtime disabled. [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization).

## Acceptance before any hosted pilot

- Synthetic accounts prove forged identity/role/family IDs, cross-family reads/writes, invite replay, expired verification and missing consent fail closed.
- Concurrent approvals, duplicate commands, cap races, retries and offline replay preserve the financial invariants; failed commands leave no partial event/projection/outbox state.
- Block between review/send, block during delivery, removed contact with an open connection and revoked session cannot receive new content; no child-visible surprise-match side channels.
- Logs/errors/network captures show no journal, prompt, unsent draft or privileged key; shared-device logout clears sensitive local state.
- Backup restoration and deletion/retention are demonstrated with synthetic records, and qualified security/privacy/child-safety review resolves jurisdiction, age policy, guardian disputes and abuse response.
