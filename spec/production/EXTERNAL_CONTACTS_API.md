# External trusted contacts

2026-11-16. Migration `202611160008_external_contacts.sql` is held as `.sql.pending` for master review and serialized execution. No SQL, account, deployment, email or push transport was executed by this helper. This extends communication authority; it creates **no** family membership, guardian power, financial access, journal access or recovery power for an outside adult.

## Invitation and consent flow

The existing `request_contact(familyId,email)` remains a same-family request. It does not become a directory or a way to notify an unknown outside child/adult. External contact uses a recipient-bound random invitation shared outside Between Us through an already known person. No email is sent and the response explicitly says `delivery:'notSent'`.

For a guardian-managed introduction, a current guardian selects their enrolled child record and the known recipient's login email/technical alias, then issues an invitation. No second family administrator must approve this guardian's own management action. The **source child still independently accepts** the introduction, the intended recipient redeems the token under their own current Auth identity, and an independent verification operator reviews the relationship. A guardian cannot accept as the child or verify their own family relationship.

A child can instead submit an addition request. That action records the child's own intention; it does not issue a token or contact a recipient. Their guardian reviews the submitted identifier and explicitly issues the one-use material. If the recipient is another child, that child's separate active identity/consent and **their own family's current guardian approval** are additionally required before verification or messaging. All ages use these guardian and consent rules.

The source child/guardian sees their own request record for both nonexistent and existing recipient identifiers. Issuance performs no account lookup. Recipient redemption cannot reveal the target to the requester until mutual acceptance. Pending external peer names/UUIDs and another family's IDs are masked; the own export follows the same rule. Recipient email means only the supplied account binding, not proof of safe identity or relationship. Local synthetic mode accepts reserved `.test` identifiers only. A generated child alias is a technical login identifier, not a mailbox.

## New authenticated RPCs

| Signature | Result and authority |
| --- | --- |
| `invite_external_contact(p_family_id uuid,p_child_id uuid,p_recipient_email text)` | Current source guardian. Resolve the child Auth UID privately from the authorized registry ID; `p_child_id=NULL` selects the caller's own adult contact. Cannot act for another adult. Returns `{invitationId,token,status:'readyToShare',delivery:'notSent',expiresAt}`. |
| `request_external_contact(p_family_id uuid,p_recipient_email text)` | Current enrolled child in that family only. Returns `{status:'requested'}` whether or not any target exists. No token, lookup, message or recipient invalidation. |
| `list_external_contact_requests()` | Latest 50 own/guardian-managed records: `{id,familyId,subjectUserId,subjectChildId,subjectName,recipientEmail,sourceAccepted,status,expiresAt}`. These names/IDs describe the caller's own authorized source subject. Status is `approvalRequired`, `pending`, `connected`, `expired` or `revoked`; pending does not reveal target redemption. No tokens, hashes, target UUID or target name. |
| `approve_external_contact_request(p_invitation_id uuid)` | Current source guardian issues a child-requested invitation once. Same material as direct issuance. Cannot reissue/renew a used invitation. |
| `accept_external_contact_source(p_invitation_id uuid)` | Only the independent source identity can accept its own guardian-created introduction. Works before recipient redemption, so the operation itself does not test target existence. |
| `accept_external_contact_invite(p_token text)` | Current intended recipient only, matching normalized Auth email/alias; source approval/membership, target account/consent and expiry rechecked. Returns `{status:'accepted',verification:'stillRequired'}`. No family membership is inserted. |
| `revoke_external_contact_invite(p_invitation_id uuid)` | Source subject or current source guardian. Cancels pending token; if redeemed, revokes the relationship and suppresses queued/leased notifications. |

Invitations use 32 random bytes, SHA-256 hashes in private storage and a one-day redemption deadline; unapproved child requests have a seven-day review window. The token is returned once, never stored in plaintext or placed in user metadata. Keep it out of logs/analytics/notification payloads. Child request and direct guardian issuance are limited to five per minute/caller. Root's HTTP/API transport still needs global abuse controls; database success counters do not count rolled-back invalid calls.

Both endpoints accept independently. Source child intention from their own addition request is distinct from guardian approval; a guardian-created request leaves source acceptance NULL. Recipient redemption binds a new canonical pair only. Existing pairs, including blocked or removed ones, cannot be silently recreated by fresh or old invitation material. Resolving an intentionally removed relationship requires a separately reviewed process; there is no automatic unblock/reopen endpoint.

## Existing RPC changes

- `approve_contact(contactId)` approves only the child endpoint(s) for which the caller is a current guardian. One family cannot set another family's child approval. Recording approval never erases either participant's private block.
- `verify_contact(contactId,operatorId,method,evidenceRef)` remains **service-only**. The operator must have active verification scope, a usable account, no endpoint role, no approval role and no guardianship in either bound family. Both acceptances, both current child approvals/consents and reviewed method policy are required. Email ownership/checkbox/parent approval never substitutes for independent verification.
- `list_contacts()` preserves legacy fields and adds `external,managedChildId,managedChildName,peerCategory`. `a/b` may be NULL for a pending external peer; names and category remain NULL until mutual acceptance. For an actual participant, category is `parent` only for a current guardian of the caller child's family, `child` for an enrolled child profile, and otherwise `trusted-person` (uncertain, never a fabricated teacher classification). Prepared-journal recipient selection must exclude uncertain categories whenever any category exclusion exists, alongside current canExchange/verification and peer ID/name exclusions. `familyId` is the caller's own relevant family or NULL for an outside adult, not the other household's identifier. A recipient guardian can see their own managed child's name without learning the unaccepted peer's name/ID. Source requesters/guardians use their always-present outgoing request record until mutual acceptance.
- Outside accepted adults can list their own conversations, send/fetch/ack authorized messages and block/revoke the relationship. These rights do not imply family administration. A parent-kind profile with no membership cannot read the child's family context or financial scope.
- Fetch after block/revocation still distinguishes the caller's own sent/previously acknowledged history from queued/new inbound bodies. It never retracts bytes already received or claims that provider acceptance is device receipt.

`restrict_contact(contactId,operatorId,reason,evidenceReference)` is service-only for an independent active safety operator. It records a private `guardian_dispute`/`safety_review` flag, prevents new exchange/delivery and suppresses pending notifications. Cross-family overlap of approving guardians automatically adds a private review flag and fails closed. Ordinary approval, verification or membership changes cannot clear a flag. No public response discloses its cause/evidence or automatically alerts an alleged unsafe person. A qualified dispute-resolution/reopening procedure remains a release gate. Confidential case operators now must be independent of both reporter and reported household, not merely the reporter's household.

## Shared locks and current authority

Contacts retain source `family_id` and gain `family_a_id/family_b_id`. Children bind their own family; an outside adult can have a NULL endpoint family without receiving membership. Legacy rows/default inserts retain their original family bindings.

`contact_family_ids(contactId)` supplies the sorted distinct source and endpoint families. `lock_contact` takes **all** those family advisory locks before the canonical pair lock and contact row lock. Existing send, conversation creation, acknowledgment and transport reauthorization already call that helper; block/revoke/fetch are extended to the same protocol. Each use rechecks current account, child membership/consent, independently current approvals, blocks, verification expiry/operator status and review restrictions.

Invitation mutations take a per-invitation mutex first, then their complete known family set, then pair/contact rows if bound. Ordinary contact RPCs never acquire that invitation mutex after family/pair locks. Notification leasing prelocks the **union of all families in its bounded batch**, globally sorted, before taking any pair/outbox row. The privacy lifecycle helper similarly snapshots relevant contact IDs and prelocks their full family union before any pair; it does not discover and acquire lower families halfway through a locked batch.

No raw contact/message/invitation/flag tables are published. Notification payloads remain neutral and service transport must reauthorize immediately before attempting delivery. A recipient's revoked session/device, withdrawn child consent or revoked approving guardian denies delivery even when a message was queued or leased earlier. No new notification transport or staffed support promise is enabled here.

## Privacy lifecycle and remaining gates

Own exports gain scoped invitation metadata, with no bearer/hash, target redemption state, hidden peer ID or review cause. Source account suspension/closure and membership revocation cancel retained invitation bearers; closure also redacts stored recipient email in affected request records. This supplements the existing partial deletion/access-revocation workflow and does not claim full deletion of shared messages, financial evidence, backups or device journals.

Service-only `run_external_contact_retention(p_subject_id,p_operator_id,p_limit DEFAULT 100)` uses the existing approved privacy/retention gates and finite identity holds, and removes at most 100 unredeemed source requests that have expired for at least 30 days. Shared redeemed invitations and confidential review evidence remain explicit reviewed-retention/purge work; the result says `sharedRecordsRequireReview:true`. Do not claim complete legal retention coverage or enable real child data until that multiparty policy is approved. The existing privacy execution remains partial and reports its blockers.

Root must execute it with all existing suites and actual cross-process send/block/revoke/lease/privacy concurrency checks. This helper has not executed migrations, pgTAP or live transport.
