Root reproduced **two failures in the initial 15-assertion qualification SQL run** before later consent/strict-type extensions; JWT and session expiry checks accepted stale authority. This was direct SQL evidence, not an exploited HTTP incident. Root subsequently applied migration `202611160025_current_actor_clock.sql` and reported **951 SQL assertions across 20 files passing**. Root also reported **17 integration tests passing**, including the real session/family lock-wait controls. These are attributed execution results, not an independent retest by this reviewer.

The correction checks a strict finite JSON numeric expiry and actual session deadline **after acquiring the session SHARE lock**, uses the live database clock for current account/consent eligibility, and rechecks the already-held session after finance's family lock. Own-privacy admission and trusted reauthentication recording receive the same post-session-lock check; a wait consumes the original five-minute proof interval. Parent-finance export rechecks its original session after existing family/account/job locks and timestamps its guarded source snapshot after the bundle read. Lock order and existing grants are preserved; the new private helper grants no client access. Actual session-row and finance-family-wait tests include observed lock positive controls and wait until the database clock passes the deadline before release. PostgreSQL distinguishes [transaction-start time from the changing live clock](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT) and documents [SHARE lock conflicts](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS); a clock check evaluated before waiting is insufficient.

**Remaining in-flight semantics:** this does not establish that every operation rechecks JWT expiry after every subsequent wait or immediately before publishing bytes. Contact/message APIs admit the actor before relationship/family waits, then recheck current relationship, consent and block state; a JWT can expire after that initial admission. Their session SHARE also serializes session deletion rather than retroactively cancelling a request that already holds it. Independently qualify expiry and revocation at each required operation checkpoint, including downstream contact waits and hosted transport timeouts. Do not claim universal instantaneous revocation from the new helper, a local SQL pass or a received Realtime hint. No broad unreviewed rewrite of all callers is included.
