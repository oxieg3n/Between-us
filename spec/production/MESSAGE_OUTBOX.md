## Boundary and intent

Only the final explicit **Send** approval may call `persistApproved(envelope,{explicitSend:true})`. The immutable `ReviewedMessage` retains the original UUID, authenticated author, conversation, peer, exact body, one of `listen|reply|later|talk`, and optional recipient exclusions. Review preparation stays in memory. This store does not import, open or copy any journal, protected draft or finance data. It never sends anything. Explicit recovery uses `loadRecovery()` to preserve each command's approved/saved/rejected status; `loadPending()` supplies approved envelopes only. The coordinator adopts the exact envelope with `{attempted:true}` for visible same-ID retry or terminal cleanup; editing an uncertain command or assigning a replacement UUID is prohibited until its outcome is resolved.

Persist must finish successfully **before** the first network send. An exception after commit can still leave a valid recovery record; it must not trigger a send or erase. Transport failure, timeout, logout, missing receipt and process death are unknown outcomes. They retain the command. A successful sender-owned receipt or successful exact send confirms `saved`; only an explicit, definitive server rejection confirms `rejected`. After an uncertain first attempt, a later blocked/expired/authorization denial proves only that the retry was denied: the first attempt may already have committed. Query the sender's receipt where possible; unknown or inaccessible remains uncertain. Do not mark that command rejected, delete it or replace its UUID based on a later retry denial alone. `resolve(envelope,outcome)` compares the entire canonical command before changing status; `removeResolved` requires the same command and terminal outcome. Uncertain records have no automatic expiry. Storage is bounded to 100 records per scope and refuses new approval when full rather than silently discarding uncertain work.

## Device and key model

The native adapter uses existing Expo SQLite SQLCipher, 32 bytes from Expo Crypto, and SecureStore `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, with a dedicated outbox keychain service. Issuer plus author UUID is hashed with existing Expo SHA-256 only for a filesystem/key alias; this is not a new encryption scheme. The SQLCipher key, filename prefix, schema and lifecycle are separate from the strong-biometric journal vault. **The directories are also separate:** the native `BetweenUsProtection` module supplies a fixed outbox sibling through `prepareMessageOutboxDirectory` / `protectMessageOutboxDirectory`. Android uses `no_backup/between-us-message-outbox`, separate from `no_backup/between-us-vaults`; iOS has a separate fixed Application Support child, with code to reapply/read back backup exclusion. iOS runtime qualification remains unperformed. Each operation reapplies native protection to database/sidecars; no public Documents/cache/plain SQLite fallback exists. SQLCipher presence and an actual encrypted schema read must succeed before use. Keys and content are never logged.

The earlier shared-directory design conflicted with the journal's strict orphan-file checks. Native source now preserves those checks and refuses unsupported/old builds without the new outbox APIs. Legacy `message-outbox-v1-*` files in the old journal directory make new outbox preparation fail closed before a replacement is created; source never silently moves, deletes, resets or overwrites them. Any existing synthetic legacy records need an explicit reviewed recovery decision. Source path separation and an empty journal directory are not proof of first journal enrollment after outbox use.

This key can be used by the app while the OS is unlocked, without a biometric prompt. It deliberately provides different availability and protection from the journal. An attacker controlling an unlocked OS/app process, malicious build, compromised account, screenshots or already-rendered content is outside this at-rest boundary. Shared OS accounts, device passcode policy, app switch concealment and physical backup/restore behavior need owner review and device evidence before release. Root must conceal/release pending UI on background, signout, identity/session changes and authorization failure. This storage adapter does not claim to clear root-owned React state.

Every open/read/write checks managed `getUser`, server-verified claims and active `get_context`, exact issuer/author, then rechecks the same managed session before exposing results. It fails closed offline, after consent withdrawal/revocation, on unsupported native/cipher/protection, malformed data, unknown schema or changed account. Root's send path independently rechecks current connection, acceptance, verification, blocks, consent and session before transmitting. Receipt access never restores permission to send.

If a database or sidecar exists without its device-only key, do not generate a replacement, reset or delete it. Wrong/unavailable keys and corrupt storage require an explicit reviewed recovery decision. Device replacement/uninstall/key loss may permanently lose the local command and its UUID; the server may still hold a message whose local acknowledgement was lost. Reinstall is not evidence that a send failed. Account recovery does not recover this key. There is no cloud outbox sync, key escrow or automatic key rotation. A key written just before an interrupted initial database creation can safely be reused only for that same scope. Backup exclusion is not a guarantee against a compromised OS.

## Interfaces and release qualification

`createMessageOutbox({issuer,authorId})` returns `persistApproved`, `loadPending`, `loadRecovery`, `resolve`, `removeResolved`. `loadPending` returns approved envelopes only; `loadRecovery` returns `{message,status:'approved'|'saved'|'rejected'}` for all own recovery records. Root must use `loadRecovery` at restart and preserve each explicit status. Exact-terminal `persistApproved` is idempotent and leaves the terminal status intact; it never changes a saved/rejected record back to approved. Changed commands under that UUID conflict. Native implementation serializes all database operations per issuer/author across factory instances; closes each connection after the operation; SQLite transactions enforce exact-command compare/update. Base/web implementation is unsupported and rejects persistence. No startup timer, retry worker or notification hook invokes send.

Migration 022 adds authenticated `get_message_receipt(p_client_id uuid)` -> `{status:'saved',clientId,messageId,conversationId,peerId}` or `{status:'unknown',clientId}`. It checks the current ordinary managed actor plus active usable account and only searches `sender_id=currentActor`. It returns no body, response, recipient acknowledgement, other sender match or contact status. Unknown includes absent/pruned records and never proves permanent non-delivery. A blocked connection can retain its sender's opaque saved receipt; the separate send RPC still denies retransmission. No table or service-role client grants are added. ## Explicit-submit transport adapter

`makeReviewedMessageTransport({outbox?,receipt,sendCurrent})` returns the coordinator's `(message:ReviewedMessage)=>Promise<void>` send callback. Create and retire it with the verified author/issuer/session coordinator. Native integration must supply its durable outbox. Web may deliberately omit it only with a visible memory-only restart limitation; the adapter does not silently switch to memory after a native persistence failure. Root's `receipt` and `sendCurrent` ports capture expected author UID and current session; `sendCurrent` keeps existing server authorization and recipient-exclusion checks.

On every explicit submit the adapter freezes a command copy, persists it first, then inspects exact own recovery status. Known saved/rejected records run only terminal cleanup, with no receipt or send. Otherwise it requests the current sender receipt. Saved receipts must match client UUID, conversation, peer and a valid saved message UUID; mismatches retain recovery and never send. Unknown receipts keep the same UUID for `sendCurrent`. Successful send or matching saved receipt records saved then removes only that exact terminal command. No code path automatically records a network denial as rejected.

All raw port failures become sanitized errors; in particular a raw `confirmedRejected:true` on a later retry is not propagated. An approved/uncertain command remains pending after an unknown receipt plus denial. `saved-cleanup` errors carry `knownSaved:true` and retain coordinator state so visible retry can finish cleanup. A durable saved terminal remains saved even if a later server receipt was pruned. If saving the terminal status itself fails, a same-instance exact-command cache prevents resend during cleanup retry. Process death before that status can be made durable cannot preserve volatile knowledge; the remaining approved recovery must use the receipt protocol. This is an explicit failure/recovery limitation, not a claim that receipt absence proves the original send failed.

Definitively rejected terminal records are preserved by storage and the adapter performs their cleanup without sending. Only an already durable rejected record, successfully cleaned, produces `confirmedRejected:true`; ambiguous network failures and rejected-cleanup failures do not. Root must not invent rejected terminal records from later contact revocation. A lost cleanup response may leave a record for later explicit recovery; it must never trigger a background transmission.

Focused transport tests cover persistence failure before any network call, original-ID coordinator adoption after restart, saved receipt without send, block following earlier success, unknown plus later denial, wrong receipt scope, durable saved-terminal cleanup failure across adapter restart with remote receipt absent, volatile known-saved cleanup retry, rejected terminal recovery and explicit web memory-only behavior. Root integration clears reviewed drafts by current-content CAS, removes the matching recovery-list entry and keeps saved confirmation distinct from a later denied history fetch. Actual interrupted native restart now has the scoped P3 pass above; final UI reruns and wider device qualification remain separate. Android capture protection for chat/Review stays enabled; do not bypass `FLAG_SECURE` to obtain private-word screenshots.
