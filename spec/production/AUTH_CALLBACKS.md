Checkpoint: 2026-11-16. This source work does not configure public SMTP, publish an app or approve real-child enrollment.

## Registered destinations and exchange

The approved app config scheme is `between-us`. The local Auth allowlist now contains exactly `between-us://auth/callback` and `http://127.0.0.1:8081/auth/callback`; the misspelled `betweenus` scheme is removed. `authRedirectTo()` uses Expo SDK 58 Linking: native requires the registered manifest/resolved scheme and returns the fixed destination rather than appending a development packager host; browser checks `createURL` against the exact local destination. Expo Go, another localhost spelling/port and hosted websites are not registered callback environments. Hosted/universal/app links require a separate owner-reviewed configuration; a custom scheme alone does not prove exclusive OS ownership. [Expo SDK 58 Linking](https://docs.expo.dev/versions/v58.0.0/sdk/linking/), [Supabase redirects](https://supabase.com/docs/guides/auth/redirect-urls).

The `src/app/auth/callback.tsx` route reads the raw link using SDK 58 `useLinkingURL`, requires the registered scheme/authority/path, rejects fragments, duplicate/unknown parameters and malformed or oversized codes, then calls only the managed SDK's `exchangeCodeForSession`. It never accepts access/refresh tokens or token hashes from a URL, calls `setSession`, decodes a JWT or follows a caller-supplied next destination. Error text is fixed; codes, URLs and provider errors are never logged or rendered. One pending exchange is shared across React effect replays; another simultaneous code is denied. Hardware Back and navigation gestures are disabled during this screen's pending work. The client's existing bounded transport applies to the SDK request. [Managed PKCE exchange](https://supabase.com/docs/reference/javascript/auth-exchangecodeforsession).

The installed Auth SDK forwards a runtime `data.redirectType` from its stored PKCE verifier; its public `AuthTokenResponse` type omits this extra field. The route checks the field structurally and routes to `/accounts?recovery=1` only after a successful SDK response with `redirectType === 'recovery'`. A URL `type=recovery` hint cannot grant recovery. The account UI must additionally require the managed `PASSWORD_RECOVERY` event/current matching session before exposing password change. A URL query alone is never authority. An ordinary successful confirmation routes to `/accounts` and still requires server account/context/consent checks.

## PKCE continuity and cryptography

The verifier is created by the managed SDK in the initiating app/browser. The existing native session adapter stores the SDK verifier in SecureStore. The browser review adapter intentionally uses a memory Map: a new tab, reload or full-page email navigation loses its verifier and the callback fails closed. Use the explicit eight-digit OTP form for this browser review; do not silently add browser credential persistence or accept implicit URL sessions. Links can also be consumed by email scanners; request a new link/code rather than weakening verification. [PKCE same-device/browser limitation](https://supabase.com/docs/guides/auth/sessions/pkce-flow), [email scanner caveat](https://supabase.com/docs/guides/auth/auth-email-templates).

Installed `@supabase/auth-js` source has a `Math.random` verifier/flow-ID fallback when global `crypto` is absent, and a plain PKCE challenge fallback when `crypto.subtle` or TextEncoder is absent. `installAuthCrypto()` must run before `createClient` and Auth must remain unavailable when it returns false. The native adapter verifies callable native RNG/digest surfaces and supplies only missing `getRandomValues` and SHA-256 `subtle.digest`, delegating both to Expo Crypto. It does not use `getRandomBytes`, whose documented development fallback can be weak. Existing platform methods are preserved; unsupported algorithm/input requests fail. Browser code requires its own secure-context WebCrypto and never installs a fallback. [Expo SDK 58 Crypto](https://docs.expo.dev/versions/v58.0.0/sdk/crypto/).

**This limited shim is not full WebCrypto.** In the installed SDK, `getClaims()` tests for the presence of `crypto.subtle`, then asymmetric JWTs can require `subtle.importKey` and `subtle.verify` without a missing-method fallback. Therefore mobile code must not call SDK `getClaims` with this shim. The root-owned `verifiedSessionClaims(token, expectedUID)` path instead sends the exact captured JWT to `api.get_verified_session`; PostgREST verifies its signature and the RPC validates the managed current UID/session/account before returning only `iss`, `sub`, `session_id`, `exp` and role. Journal retains online `getUser` before this call and its final unchanged-session check. No unverified local claims decoder or skipped signature verification is used. Server Node code with full cryptography is unchanged. Native diagnostics must distinguish digest support from importKey/verify support.
