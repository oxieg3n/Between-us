# Local journal vault: production foundation

Date: 2026-11-16. Status: implemented source contract for fictional-data production-foundation evaluation, with a limited observed Android diagnostic described below. This is not independent security approval or permission to collect real children's writing. Historical memory-only prototype reports remain accurate for their builds. Production release still requires the independent reviews and device evidence below.

## Decision and information boundary

Use the SDK-compatible `expo-sqlite` SQLCipher build for an encrypted local database per authenticated author and installation. Store a separate, randomly generated database key through `expo-secure-store`, protected by OS authentication. Unsent conversation drafts use a different SQLCipher database, key and adapter. Do not invent a cipher, password derivation scheme, recovery protocol or encrypted export format.

Journal content, titles, entry identifiers, timestamps, private draft text, model prompts, model outputs and native model sessions never enter the family ledger, backend, contact graph, analytics, notifications, push payloads, crash reports or message outbox. The backend has no journal table, upload/read/export endpoint, administrator key or guardian recovery capability. Account verification sends no writing. A separately composed message can enter transport only after its own explicit Review and Send; no original journal text is copied automatically. Journal export is an explicit author action described below. Local storage encryption is not end-to-end encryption, account authentication, protection against a compromised OS or proof that a trusted adult is safe.

The demo `state.tsx` role switcher, `journal.ts` saved-state comparison and `screens/Journal.tsx` memory-only labels are separate from `production/Journal.tsx`. A role selector is never authentication. `journal-intelligence` remains independent of storage/network/finance APIs and receives only the current author's explicitly permitted, bounded text in memory. Separate-message composition, Review and recipient authorization remain mandatory.

## Account binding and shared devices

There are three different authorities: an authenticated application account, an enrolled local author/vault binding, and OS permission to release a device-protected key. A family/guardian administrator is none of these for another author. Never accept a UI role, request-supplied `authorId`, family membership or a deep-link parameter as a local vault capability.

Only the account/session coordinator can bind an authenticated account subject and issuer to an opaque local vault ID. The protected enrollment manifest holds this minimal binding and lifecycle state, not content; it is not an independently verified installation identity. Never put it in AsyncStorage, URLs or a family record. Database names/key aliases use random IDs, without names, emails, roles or journal titles. Encrypted metadata also verifies author/vault/purpose after unlock. Account changes revoke the old lifetime; replacement access waits for cleanup.

An enrolled device biometric or its passcode proves control of that device, not which family member is using it. A guardian who knows the child's passcode or has an enrolled fingerprint may unlock OS-protected keys. The initial production candidate therefore supports one enrolled author per OS application installation, on an author-controlled device, with a clear shared-device warning. A second author's enrollment is refused while a vault remains enrolled. It must not silently delete or replace that vault. Supporting multiple authors on one installation requires a separately reviewed author credential/key-release design using standard platform/library facilities, coercion analysis and tested author switching. Do not solve it with a homegrown PIN, a hardcoded key, a TypeScript brand or repeated OS biometrics. Synthetic multi-author adapter tests remain required to prove namespace separation; passing them does not enable shared-device production use.

Account/session tokens use their own managed authentication adapter and protected storage. They are never SQLCipher keys, recovery keys or key derivation inputs. A password reset, family administrator action, new login or new device cannot reconstruct an existing local journal key.

## Adapter contract

The actual types live in `apps/mobile/src/production/vault/types.ts`; the portable core accepts test ports. The production browser vault is unsupported, with no plaintext/memory writer fallback. The separate demo remains memory-only. Unsupported native modules or missing SQLCipher refuse persistence. Types alone do not establish authorization.

```ts
type VaultActor = Readonly<{ issuer: string; subject: string; sessionId: string }>;
// Selected VaultController signatures; see types.ts for the complete contract.
enroll(actor: VaultActor, signal?: AbortSignal): Promise<void>;
unlock(actor: VaultActor, signal?: AbortSignal): Promise<void>;
lock(reason: 'background'|'idle'|'manual'|'signout'|'account-change'|'revoked'): Promise<void>;
list(input?: {limit?: number; before?: {updatedAt: string; id: string}}): Promise<EntrySummary[]>;
read(id: string): Promise<VaultEntry | undefined>;
save(input: SaveEntry): Promise<VaultEntry>;
delete(id: string, expectedRevision: number): Promise<void>;
listDrafts(filter?: {kind?: 'journal-editor'|'conversation'; title?: string}): Promise<DraftSummary[]>;
readDraft(id: string): Promise<PrivateDraft | undefined>;
saveDraft(input: SaveDraft): Promise<PrivateDraft>;
clearDraft(id: string, expectedRevision: number): Promise<void>;
preparePlaintextExport(ids: readonly string[]): Promise<string>;
erase(actor: VaultActor, signal?: AbortSignal): Promise<void>;
dispose(): Promise<void>;
```

Async storage failures expose fixed `VaultError.code` values, not native exceptions, SQL, keys, paths or content. `unlock` captures actor/session and generation; lock invalidates operations synchronously before cleanup awaits. Recheck that lifetime before work and after awaits, including final publication. A stale read/export cannot publish; a queued stale save cannot start. A transaction already committed before lock may persist, but its result cannot render in the next session. Rejected saves do not prove that nothing committed; reread after the same author unlocks.

Native callers use `createProtectedNativeVaultController`, wrapped by the process-wide exclusive factory. Every new lease waits for the previous controller's idempotent disposal before construction; failed retirement remains attached and prevents replacement. Journal and private-message draft screens therefore cannot open overlapping biometric-vault controllers. Direct low-level factories do not supply this ownership barrier. Callers must still immediately clear/conceal UI and cancel model work on lock and retire old screens on account/session change.

One adapter-owned serial queue is the only way to access each open database. The lock barrier synchronously revokes the capability and blocks new operations before awaiting any native cleanup. No screen holds a key, SQL handle or another author's entry collection. `list` returns at most 50 summaries; validate 1..50 and cursor shape. `read` loads a single body. Validate generated UUIDs/known identifiers, title <=150 and body <=5000 Unicode code units, nonblank body, bounded input bytes, and current revision in the adapter as well as UI. Reject oversize input rather than truncate private writing. Use bound parameters for all content and identifiers used as values. The only interpolated key pragma uses adapter-created, strictly `/^[0-9a-f]{64}$/` key hex; it must never be logged or retained for diagnostics.

Saving an existing entry requires the expected revision; update with `WHERE id = ? AND revision = ?`, increment once, and return `conflict` if zero rows changed. New entries require null expected revision and a generated ID. Deleting also checks revision; not-found reads return undefined without querying another vault. Timestamps are app-generated UTC display/order values, never security authority. Pagination uses `(updated_at DESC,id DESC)`. Each database enforces 1,000 rows and 16 MiB of title/body UTF-8 bytes transactionally; the draft quota is shared across both kinds, with no silent eviction. Deletion can free space; the in-memory export preparer does not imply an available export destination UI.

The same controller opens a physically separate draft database with its own random key; draft CRUD never accesses the journal database. Journal editor rows use `kind:'journal-editor'` and null recipient/preference; the production Journal discloses and automatically protects changed foreground writing after a 1-second pause while already unlocked. Separately composed conversation rows use `kind:'conversation'` and remain manually protected, unsent copies. Recovery must revalidate the author and current recipient and still requires Review/Send; persisted candidate/permission snapshots confer no authority. Confirmed rows remain until explicitly cleared, successfully cleared by the caller after use, or whole-vault erase. No draft is read by notifications or automatically copied to transport.

## Schema version 1

Each database contains one encrypted `vault_meta` row and the same `entries` table shape. Purpose-bound metadata selects `journal` or `drafts`; only draft rows populate kind/recipient/preference. There is no `private_drafts` table, FTS, attachment store, history, mood score, inference transcript or sync tombstone. The schema below summarizes current core.ts.

```sql
CREATE TABLE vault_meta (
  singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
  vault_id TEXT NOT NULL,
  issuer TEXT NOT NULL,
  subject TEXT NOT NULL,
  purpose TEXT NOT NULL,
  schema_version INTEGER NOT NULL
);
CREATE TABLE entries (
  id TEXT PRIMARY KEY NOT NULL,
  title TEXT NOT NULL CHECK (length(title) <= 150),
  body TEXT NOT NULL CHECK (length(body) <= 5000),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  revision INTEGER NOT NULL CHECK (revision >= 1),
  kind TEXT,
  recipient_candidate TEXT,
  response_preference TEXT
);
CREATE INDEX entries_recent ON entries(updated_at DESC, id DESC);
```

SQLite length checks are defense in depth; adapter Unicode/byte/kind validation is authoritative. Empty draft bodies are allowed; saved journal bodies must be nonblank. No `author_id` CRUD argument is needed: the unlocked session selects the vault and encrypted metadata verifies its binding. Draft recipient authorization is rechecked outside storage. Only schema v1 is implemented; unknown versions deny without migration, downgrade or reset. Never automatically import demo/plaintext fixtures.

## Creation, key custody and failure handling

1. Confirm validated own-account enrollment, supported native build, strong biometric key protection and no existing different-author enrollment or unresolved files. Explain recovery and device-control limitations before creation. Declining or lacking hardware leaves production writing unavailable; the separate demo is not a persistence fallback. Never weaken `requireAuthentication` silently.
2. Create random opaque vault IDs and independent 32-byte journal/draft keys with async native randomness. Store keys with separate SecureStore services/aliases and `requireAuthentication: true`. Read them back through authenticated access before committing enrollment. LocalAuthentication may preflight availability, but does not substitute for this read.
3. Open each database in an application-private, backup-excluded directory. Verify SQLCipher availability before schema access, then set the validated raw key with SQLCipher's documented key syntax. Do not create a table first. Leave cipher defaults, HMAC and encrypted header intact; request `cipher_memory_security = ON`, qualify support/performance, and set `temp_store = MEMORY`, `secure_delete = ON`. Use ordinary rollback journal mode for this small initial workload; no WAL/shared container/background write requirement. Any later WAL change must cover WAL/SHM/keying/backup/cleanup explicitly.
4. On existing vaults, read `sqlite_master`, check encrypted binding/purpose/schema and run the reviewed integrity checks before returning an unlocked handle. A wrong key, unknown schema or mismatch never creates a replacement. Native integration must demonstrate that opening a copied file without/with a wrong key fails; merely observing `cipher_version` is insufficient evidence that a file was keyed.
5. Persist the protected enrollment manifest as `creating` before allocating keys/files; mark it `ready` only after both stores initialize. Each schema/metadata creation is transactional, not a cross-database atomic transaction. Interrupted creation, orphan files, missing stores and unknown manifests deny as recovery-required/corrupt rather than auto-repairing or enrolling over them. A missing authenticated key never causes regeneration. `erase` can retry a retained `deleting` manifest after author/device authentication; no automatic launch-time erase is implemented.
6. Drop temporary key-byte references promptly and overwrite mutable byte arrays when possible. JavaScript strings, garbage collection, bridge copies and native allocations prevent a guarantee of complete zeroization. Never save a key in Redux, AsyncStorage, environment variables, bundle constants, SQLite tables or model settings. No shared Keychain access group.

Key rotation is deferred from the first spike. A future SQLCipher rekey flow must independently review atomic key/database replacement and crash recovery before use; changing a key alias alone strands the data. Authentication changes are not rotation and must not trigger automatic key regeneration. Losing access shows recovery information, retry and explicit author-confirmed deletion; it never silently overwrites the vault.

## Lock, session and offline lifecycle

Initial policy: conceal immediately when AppState leaves `active`; lock on real background, unrelated inactivity, logout, account change, manual lock, verified own-account/device revocation, or after two minutes without author input while foregrounded. Measure idle time monotonically in process and recheck before every operation; a suspended timer is not an authority. Every fresh process starts locked. The adapter's own LocalAuthentication/SecureStore modal can cause inactive events: retain the pending lifetime only during that narrow authenticated native operation while keeping a separate opaque privacy cover. Any true background event still invalidates generation, including during the prompt. Wait briefly for active resume, then verify active state and current actor generation before unlock or private results can publish. Cancel/deny stale prompts without looping authentication or exposing content while inactive. Physical-device qualification remains mandatory.

The vault lock revokes its local operation generation synchronously; it does not itself revoke the managed Auth token. Caller callbacks cover and clear visible entry/draft/suggestion/export state and abort reflection. Queued database/model work drains before replacement access; OS suspension may prevent cleanup from finishing. The exclusive factory keeps replacement access closed until retirement succeeds. There is no promise of OS heap erasure or a final background save. Explicit journal Back flushes or warns; involuntary lock never waits for a dialog.

Root also owns a central two-minute monotonic private-writing lifetime for the current author/account session across Home, conversation and Review. Background or timeout clears unsent conversation maps, report words and preparation/recipient-policy state, and increments a separate private-draft epoch so stale callbacks cannot restore words. Actual author input can extend this deadline; timers/results cannot. Unattempted Review is discarded; an already attempted immutable command is hidden and retained for explicit receipt resolution or exact-command retry. This root lifetime is separate from the vault's two-minute lock and does not erase confirmed protected drafts or an approved-message outbox record.

The core has no network authority and cannot independently learn revocation. Production Journal requires online managed verification on every fresh unlock and exposes no offline unlock. The approved continuation below permits only an already unlocked author's bounded local writing during a typed outage; without that valid lease, verification failures remain covered/locked. This supplies no immediate remote revocation, message permission or new-author enrollment. Never upload content to check revocation or treat guardian family/contact authority as journal authority.

Contact blocking/revocation remains separate: reauthorize the separately composed message at Review, send, delivery and retry; it cannot change private journal ownership or disclose a draft. Safety/help remains reachable while locked, offline or without guardian approval and must not include journal text.

## Approved bounded offline-writing continuation: implementation contract

The owner approved a narrowly scoped continuation for an **already online-verified and device-unlocked** Journal on 2026-11-16. At the review checkpoint before this change, Root's 60-second account check covers every route on a network failure, and Journal's refresh coordinator keeps its own opaque cover after unavailable verification; local save actions also call SDK session refresh. Together these prevent useful offline writing despite an open local vault. This section specifies the replacement boundary before behavior changes; it does not enable offline sign-in, fresh unlock, restart recovery or background resume.

One in-memory lease belongs to the exact verified issuer, subject, managed session ID, role, root account epoch and unlocked controller lifetime. Capture `performance.now()` **before the complete online verification begins**. The server lease RPC returns `{issuer,subject,sessionId,remainingMs}` only after the ordinary managed actor/current account/session checks, with integer remainingMs bounded by 900,000 milliseconds and the earlier signed JWT `exp`, current `auth.sessions.not_after` or currently qualifying child consent expiry, using the database clock. Parent own-journal leases are independent of a child's consent. The exact candidate JWT must be used for Auth user, claims, lease and context verification; all identities must match, and final token/account epoch checks must still match after the full proof. Device authentication/unlock time consumes this interval. The local absolute deadline is request-start monotonic time plus server remainingMs, never response time or last-edit time. An elapsed/zero/malformed lease grants no continuation.

Current verified-session claims expose `iss`, `sub`, `session_id`, `exp` and authenticated role, but the pre-change Journal access helper discards exp and receives no trusted server time. Device `Date.now()`, SDK cached `expires_at`/`expires_in` or an unverified decoded JWT cannot honestly establish an earlier server expiry when the device clock is wrong. The new server-computed remaining lifetime addresses this gap without new cryptography, keys, JWT decoding, persisted capabilities or journal payloads. Supabase documents the distinct [managed session ID and revocation check](https://supabase.com/docs/guides/auth/sessions) and [JWT expiry boundary](https://supabase.com/docs/guides/auth/jwts).

Only a complete fresh online proof may renew a lease. A cached context, local SDK session read, TOKEN_REFRESHED event, retry timer, editor input, autosave or model completion never extends it. The existing two-minute author-input idle lock remains independent and can expire sooner. Real background, unrelated inactivity, signout, account epoch/author/session change, verified denial, lease expiry, unmount and process restart revoke continuation immediately; a normal device-authentication inactive cover retains no new authority. No lease is written to disk or reused after a fresh process. No new offline vault enrollment/unlock is permitted.

Within a still-valid original lease, current-author local journal CRUD, private draft autosave/recovery and optional local templates/already available on-device inference may proceed without awaiting an SDK network refresh on each local action. Current SDK/Auth boundary events remain immediate cancellation signals; an unverified refreshed token cannot mint a different actor or extend the original deadline. Cached contact metadata may supply only explicitly labeled stale local reflection context, subject to all unsafe-name/category exclusions. It cannot assert current contact permission. Choosing/sending to a recipient, reports, finance, notifications, account administration, outbox recovery/retry and current-contact verification remain online-authorized operations. Whole-vault erase and plaintext-review controls retain their separate fresh verification/device-authentication requirements rather than inheriting a broad offline bypass.

Only typed network failure, timeout, HTTP 429 or transient 5xx can expose this still-valid local continuation. HTTP 401/403, SQL authorization denial, missing credentials, malformed/unknown proof, wrong identity and other unexpected failures fail closed. Client transport must preserve this distinction; converting malformed JSON or all unknown exceptions into an offline status is not acceptable. Reconnecting performs the full current proof; an explicit current denial locks and clears private writing immediately. A disconnected device cannot discover remote revocation until it reconnects or the shorter lease/idle deadline ends. This intentional bounded revocation delay needs independent mobile-security and child-privacy review; it is not immediate remote revocation.

Root may exempt **only the currently mounted Journal** from its network-unavailable overlay while a synchronous current-author/account-epoch/unlocked-lease check succeeds. Every other cloud route stays covered; global app-state/capture protection remains effective. The Journal-to-Root availability signal contains only author ID, account epoch, unlocked state and monotonic deadline, with null on retirement; it contains no text, selected page, raw token, key or model result. A cached Boolean alone must not outlive its deadline or route lifetime. Local signout and public Help remain reachable without network access.

Check the deadline synchronously before input/local-operation admission and private result publication, and use a foreground expiry timer to lock the existing controller. Timer delay cannot renew the lease or allow an expired author input to revive it. At expiry, conceal/clear immediately and cancel/drain existing work using the existing vault/model generation barriers. No final asynchronous save is promised after expiry or OS suspension; confirmed drafts remain local, and a previously dispatched native commit may persist even when its result is withheld. An outer lease does not make a completed native transaction reversible or guarantee heap wiping.

Required implementation tests: verified-online unlock followed by typed outage permits own local typing/save/autosave/model within the original deadline; cold/offline unlock denies; proof/device-unlock latency consumes TTL; TTL and two-minute idle expire independently; repeated failures/typing/refresh candidates cannot extend the cap; forward/backward wall-clock changes have no effect; malformed/nonfinite clocks/proofs and changed author/session/epoch deny; no stale awaited read/write/export/model result publishes after expiry; background/unmount revokes with no resume; fresh denial overrides an otherwise valid lease; successful full same-session proof alone renews; Root's route-specific cover never opens messaging/finance/contact actions. Pure ports tests do not establish native suspension, stored-key custody or actual offline device behavior. No behavior/source change or native check was made during the initial contract review.

The source implementation now uses `journal-offline-lease.ts` plus optional lease ports in `journal-access.ts`; existing online-only message-draft/outbox verifiers do not inherit offline grants. Journal proof reads only a synchronous unverified candidate, then exact-token managed Auth user, server claims, lease and context through typed transport; it never relies on SDK retryable0 or an SDK network refresh to authorize continuation. Every local action, draft-authorized callback and model author-version check consults the live lease. A one-second non-touch check retires expired access; a side-effect-free external-store snapshot also hides an expired writer at render before the timer callback. Full online rechecks run on a 60-second interval and explicit requests/token-refresh events, without extending idle time. Only a successful current proof may renew; a late success after expiry cannot revive a locked writer. See the separate [server lease contract](JOURNAL_LEASE_API.md).

Contact snapshots refresh separately after a successful online proof and never grant storage authority. Manual and while-writing reflection use that last snapshot locally with the same unsafe-name/category exclusions and explicit stale-metadata disclosure. No local action routes through an SDK session refresh. Privacy review, erase and recipient handoff still require their explicit online proof; sending/finance/contact administration remain outside the lease. Actual offline native typing/save/autosave/reconnect/revocation/expiry interactions remain root-owned qualification gates.

A full 255-test mobile run passed before the last added outage-to-draft integration case; the final 22-test offline/access run passes, including nine lease cases. ## Backups, recovery, deletion and export

Exclude both databases, rollback/WAL/SHM sidecars, draft stores, enrollment markers and any export temporary files from OS/cloud backup and device transfer. On Android, use the correct private directory plus explicit legacy backup and current data-extraction exclusions for every actual path; `allowBackup=false` alone does not reliably disable all manufacturers' device transfer. On iOS, set and verify the directory/file backup exclusion using the platform resource attribute through a reviewed config plugin/local native module if Expo lacks the needed surface; reapply and verify after saves/moves/replacements because file operations can reset it. Do not assume `Paths.document` is excluded. Do not put a durable vault in an evictable cache directory just to avoid backup. [Android Auto Backup](https://developer.android.com/identity/data/autobackup), [Apple backup exclusion](https://developer.apple.com/documentation/foundation/urlresourcekey/isexcludedfrombackupkey).

The selected SecureStore accessibility prevents intended key migration, but does not replace these file exclusions. Treat iOS reinstall-surviving Keychain items as possible orphan secrets: a missing installation marker never automatically reattaches a surviving key to a new login. Explicit local vault removal deletes all known vault service aliases. Test uninstall/reinstall and device restore on each platform; do not promise uninstall alone securely deletes iOS keys.

Recovery notice before first save: **These pages are stored on this device. We cannot recover them if the device or its key is lost. Changing device security settings can make them inaccessible. Your parent, guardian and the service cannot unlock them for you.** Device loss, uninstall, biometric invalidation, passcode removal, corrupted storage or lost keys may mean permanent loss. No cloud backup, parent escrow, support override, password-reset recovery, multi-device sync or recovery phrase is included. A reviewed future recovery strategy is a separate explicit decision and cannot retrospectively recover lost keys.

Delete one entry under its revision transaction; clear matching editor state, reflection and selected export snapshot. `secure_delete` and file maintenance reduce reachable remnants, but flash wear leveling, OS snapshots and already exported copies prevent a promise of per-entry forensic erasure. No retained soft-delete history or tombstone is needed locally. Keep entries until the author deletes them; conversation drafts remain only until sent/discarded or the author erases the vault. A resumed draft is always identified as unsent.

Erase the whole enrolled vault only after fresh own-author/device authentication and explicit destructive confirmation. The adapter revokes runtime access, drains/closes handles, marks `deleting`, removes both keys/files/sidecars and finally removes the manifest. An interrupted erase is retried by an explicit authenticated erase request; it never reports success after a failed removal. Key destruction cannot revoke exported copies or guarantee physical flash erasure. Remote guardian/admin account deletion cannot decrypt/export the journal; retained local-vault behavior after account deletion remains a product/privacy release gate.

`preparePlaintextExport(ids)` performs fresh device authentication and returns selected entries as a bounded JSON string in memory. Production Journal now exposes an unlocked-only selected-page **readable review**, limited to five saved pages per review, using that existing core format. It is not a completed portable export or encrypted backup. It excludes editor changes and private drafts; there is no destination, file creation, clipboard, auto-share, family account download or administrator export. Any future artifact surface still requires separately reviewed destination/disclosure/temporary-file cleanup; no invented encrypted export/recovery format is implemented.

## Own-author storage controls

From the unlocked pages list, **Manage my private journal storage** progressively reveals readable-review selection and whole-vault deletion. Only pages returned by the current own-vault list can be selected. A separate confirmation explains plaintext disclosure before the core requests fresh device authentication. The bounded memory review clears when selection changes, controls close, page/editor changes, the journal locks/backgrounds, or the author/session lifetime changes. Transient covers hide the review; an awaited old selection/lifetime result cannot publish. The review uses ordinary nonselectable Text inside the existing protected Journal surface, without an external destination. Clearing UI references does not guarantee JavaScript/native heap zeroization.

Whole-vault deletion is available only in this already unlocked own-author flow. Its destructive confirmation requires typing `DELETE` and explains that all saved pages, both kinds of protected private drafts, and the two biometric-vault keys are removed; shared messages, the separate approved-message outbox and external copies are outside the action. The screen suspends/drains draft protection, cancels suggestions, closes editor state and awaits model retirement, then obtains a fresh managed actor matching the original author/session before invoking existing core `erase(actor)` and its fresh device authentication.

Core erase intentionally invokes onLock immediately. The UI therefore does not reuse the old unlock AbortSignal, which its own lock aborts, and retains a separate erase-in-progress gate until the operation settles. Unlock/re-enrollment cannot overlap deletion. Only the single expected intentional lock and unchanged active account may receive a success notice; extra background/account events withhold stale results. Cancellation/partial failure reports that deletion was not confirmed and never resets storage or claims that all prior data survived. No automatic erase/recovery is added. An interrupted `deleting` state that cannot unlock still requires a separately reviewed own-author recovery/erase-retry surface; these unlocked-only controls do not bypass that restriction.

## Separate approved-message recovery

The approved-message outbox has its own database, schema, key/service and `approved-message-outbox` purpose. It never opens either biometric vault database or reads a protected draft. Only explicit Send approval may persist the exact separately composed immutable command, before transport; unknown outcomes retain the original UUID/body/recipient/preference for visible explicit retry. No timer, startup recovery or outbox API automatically sends. Current server authorization is checked independently before transmission; a receipt does not confer send permission.

Unlike journal/draft keys, the outbox key uses device-unlocked `WHEN_UNLOCKED_THIS_DEVICE_ONLY` without a biometric prompt. Operations verify current managed author/session before and after storage work, deny offline, and close their own connection. This purpose separation is intentional, not equivalent biometric protection or journal synchronization. See [outbox contract](MESSAGE_OUTBOX.md) for exact resolution, capacity, key-loss and remaining native/recovery gates.

The native module now assigns the outbox a separate fixed sibling: Android `no_backup/between-us-message-outbox`, iOS Application Support `BetweenUsApprovedMessageOutbox`. Journal/draft paths (`between-us-vaults` / `BetweenUsPrivateVaults`) and strict orphan rejection are unchanged. Outbox preparation/protection refuses any legacy `message-outbox-v1-*` filename in the old vault directory; it does not migrate, delete or silently replace an uncertain command. Affected staging users need an explicitly reviewed recovery path. Old native builds lack the new methods and fail closed until rebuilt. Root must verify first Send before initial Journal enrollment and legacy refusal after native rebuild; source separation alone is not an executed regression.

The owner-authorized production Journal protects in-progress journal edits after a 1,000 ms foreground pause, only inside an already unlocked own-author vault. Each open editor receives a distinct lifetime stamp. New/saved pages start without a draft write; recovered drafts seed the existing private ID/revision and current content. Only changed snapshots schedule a write, and a single in-flight operation owns the next revision.
