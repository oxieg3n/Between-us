# Native transport configuration — source preparation

Prepared 2026-11-16. `apps/mobile/plugins/withProductionTransport.cjs` is an unregistered config-plugin source until root reviews and registers it. This work does not modify app config, generated native files, signing material, packages or global settings, and does not run prebuild/native builds. No release artifact or iOS runtime has been verified by this plugin task.

## Observed source and intended output

The reviewed generated Android main manifest had no explicit `usesCleartextTraffic` flag. Its debug manifest explicitly permits cleartext and replaces the main flag, supporting Metro/local synthetic services. Release JavaScript endpoint validation already rejects HTTP. That JavaScript guard does not substitute for native transport configuration.

The plugin uses the installed Expo `withAndroidManifest`, `withAppBuildGradle` and `withInfoPlist` mods. Expo documents these as transformations of the parsed main manifest, Groovy app build file and parsed Info.plist during prebuild. Existing source was inspected rather than inventing another build framework. [Official Expo mods](https://docs.expo.dev/config-plugins/mods/), [plugin registration and execution](https://docs.expo.dev/config-plugins/plugins/).

Root should register this plugin after the existing production-signing plugin, run prebuild serially only after current native work finishes, and review the resulting diff. Registration is not performed here. Only the plugin's own marked Gradle block is replaced on rerun; signing, backup rules, permissions, callback intent filters, device-vault code and other plugins are preserved. Ambiguous/interrupted markers or an unmanaged use of its placeholder/check name fail for review. Unsupported non-Groovy or changed Android templates fail rather than silently skip enforcement.

## Android release checks

Android documents that `usesCleartextTraffic=false` is a platform policy and that a Network Security Config overrides this flag on API 24+. The plugin therefore rejects a main-manifest `networkSecurityConfig` and rejects removal of its cleartext attribute; merged release output checks reject any custom network config as well. A future legitimate certificate/network configuration needs explicit review, not silent replacement. Platform enforcement also depends on the networking stack; this is not a promise that arbitrary native raw sockets are automatically secured. [Android application manifest reference](https://developer.android.com/guide/topics/manifest/application-element#usesCleartextTraffic), [Network Security Configuration](https://developer.android.com/privacy-and-security/security-config).

Every app task whose name contains release depends on `verifyBetweenUsProductionTransport`. The task checks final default/release placeholder values, release debugging off, no unreviewed product flavors, the expected `processReleaseMainManifest` task and the unchanged main-manifest placeholder/no custom policy. Every release process-manifest task gets a post-action check: find its actual output `AndroidManifest.xml` files, reject missing/changed output layout, parse XML without DTD/XInclude expansion and require cleartext=false, no custom network policy and no debuggable=true. This detects later Gradle/manifest merges that would otherwise silently override the release setting. It uses existing Gradle task/output APIs; no additional Gradle dependency or native file writer is added. [Gradle task configuration](https://docs.gradle.org/current/userguide/task_configuration_avoidance.html), [task output API](https://docs.gradle.org/current/javadoc/org/gradle/api/tasks/TaskOutputs.html).

These checks intentionally depend on the reviewed generated template/task/output conventions. Their source tests do not execute AGP or prove a final APK/AAB. A changed AGP/template/output layout must block for review; never remove a guard just to obtain a build. Existing owner-controlled release signing gates remain separate and may stop a release before manifest processing. No debug key or signing fallback is introduced.

## iOS ATS scope and retained local exception

Apple documents `NSAllowsArbitraryLoads` as disabling ATS broadly; the media/web-content keys provide other broad exemptions. This plugin explicitly turns all three off. [Apple arbitrary-loads key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowsarbitraryloads), [ATS dictionary](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity).

The owner approved retaining Expo's explicit `NSAllowsLocalNetworking` development exception rather than adding unverified per-configuration plist generation. It can permit local resources such as unqualified/local names and IP connections under Apple's version-dependent rules. It is present in the shared plist, **including release**; do not claim iOS denies every local HTTP connection. Release JavaScript endpoints still require HTTPS. Hosted endpoints cannot use this local exception as approval to weaken TLS, and existing arbitrary domain exceptions fail review. [Apple local-networking key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking).

No iOS project, archive, device, ATS behavior, local-network permission or Metro connection is qualified here. Before listing iOS support, inspect the generated plist and signed archive, reconcile deployment targets/SDK networking stacks, and test the actual desired local/debug and release HTTPS behavior on the approved devices. Removing the local exception or generating separate Debug/Release plists is a future reviewed choice, not a completed feature.
