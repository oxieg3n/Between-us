## Finding: shared sequential IDs expose hidden activity counts

**Status: CLOSED for the fictional prototype. The sequential counter was removed, regression checks passed and native UUID execution is evidenced across the unchanged helper's r11/r12 use.** The original severity was a moderate prototype privacy defect. It exposed a count of unseen ID allocations, not journal text, matching amounts or a reliable identification of which hidden action occurred. This closure does not certify production identity, timing privacy or server authorization.

Before correction, `model.ts` generated globally increasing `local-1`, `local-2`, etc. The same factory creates private journal entry IDs in [`state.tsx`](../../apps/mobile/src/state.tsx#L249) and finance command/goal IDs in [`finance-state.tsx`](../../apps/mobile/src/finance-state.tsx#L34) and [`Finance.tsx`](../../apps/mobile/src/screens/Finance.tsx#L574). Child-visible activity renders `Reference: {item.referenceId}` in [`Finance.tsx`](../../apps/mobile/src/screens/Finance.tsx#L1502).

Read-only reproduction with the actual factory and financial domain:

1. Create a child's goal: its visible reference is `local-1`; its event consumes `local-2`.
2. Configure parent matching: its hidden event consumes `local-3` and is correctly omitted from the child's DTO.
3. Create another child's goal: its reference is `local-4`, rather than the `local-3` reference obtained without the hidden operation.

Private journal creation uses that same counter. Consequently DTO filtering alone cannot keep the number of intervening private allocations unobservable. This differs from the known process-memory/debugger limitation: ordinary child-visible references carry the sequence.

The integrated correction preserves `newId()` callers and the `local-` prefix while using independent UUIDv4 references: existing Expo `uuid.v4()` in [`id.native.ts`](../../apps/mobile/src/id.native.ts), standard `crypto.randomUUID()` in [`id.ts`](../../apps/mobile/src/id.ts) for Web/Node. There is no timestamp, counter, `Math.random` or weak fallback, and no new dependency. These IDs are references, never authentication or authorization tokens.

The candidate was prepared at `D:\GameDev\Temp\betweenus-opaque-ids-4f3d26dc` without touching watched source during frozen r7 native QA. After that run, the master integrated the helpers and [`tests/id.test.ts`](../../apps/mobile/tests/id.test.ts). The three tests fail against the original counter and pass against the isolated candidate. They cover UUID delegation/shape, fail-closed behavior, and real-domain interleaving of hidden matching configuration/funding and private journal allocation with child-visible goal/event references. The interleaving test retains hidden-reference exclusion and unchanged child financial projection assertions; it does not replace existing DTO tests.

Follow-up read-only inspection confirms [`model.ts`](../../apps/mobile/src/model.ts) imports and reexports the helper, so existing journal, contact, check-in and finance callers retain one API. `createMessage()` uses the helper too, eliminating its former alternate identifier construction while retaining contact verification and nonempty-message checks. A source scan found no sequential factory, timestamp-derived ID or weak fallback in these callers. The clean [r11 light native proof](../qa/chores-goals/1115-r11-native-usability-v2/QA_REPORT.md) checked an exact UUIDv4 financial reference after journal creation and hidden matching actions. The master verified the ID module has no diff from `f0c888a` to `8607573`; current [r12 native interactions](../qa/chores-goals/1116-r12-native-interactions/QA_REPORT.md) successfully created journal entries and simulated messages through that unchanged native helper in both themes.

No fresh r12 financial UUID-format screenshot was captured. Closure rests on removal of the counter, delegation/fail-closed/interleaving regressions, the valid exact r11 financial-format proof, unchanged ID implementation and current r12 native calls, rather than inventing that missing screenshot or implying the counter remains unfixed. These identifiers remain opaque references, not authorization credentials. Broader traffic/timing correlation or authenticated multi-user privacy is outside this prototype finding.

Installed-source provenance was checked: Expo `58.0.25` exports `uuid` through `expo-modules-core` `58.1.0`; its native wrapper calls `globalThis.expo.uuidv4` and throws when absent. Android `CoreModule.kt` uses `UUID.randomUUID().toString()`; iOS `CoreModule.swift` uses `UUID().uuidString.lowercased()`. The [versioned Expo 58 reference](https://docs.expo.dev/versions/v58.0.0/sdk/expo/) documents the export. Actual Node 26 and headless Chrome on an ephemeral secure localhost origin successfully invoked standard `crypto.randomUUID()`. This is platform availability evidence, not an integrated mobile UUID test.

## Finding: a blocked person could create a new reverse incoming message

**Status: CLOSED for the fictional in-memory prototype. R12 source/unit/browser checks and focused native confirmation passed.** Production authentication, server authorization and delivery revocation remain separate release gates. This was actual fictional app behavior, independent of the known demo-authentication limitation.

Before r12, `changeContact()` altered only one shared Contact row, and `createMessage()` checked only its recipient. Reproduction with actual model/thread code confirmed both cases: child blocks Alex, switch to parent, create a message to still-verified Sam; parent blocks Sam, switch to child, create a message to still-verified Alex. Both new messages were accepted and appeared in the recipient's thread. Existing tests covered blocking the outgoing recipient, so they missed the incoming direction. There was no Unblock UI; the parent update API could overwrite a blocked status with approved while resetting acceptance/verification, but it had no independent record of who owned the block.

R12 keeps author block edges separately from administrator-managed base contacts. [`communication.ts`](../../apps/mobile/src/communication.ts) projects one's own block as blocked and a reverse Sam/Alex block as generic messaging unavailability without naming its owner. `canExchange()` denies either directed edge, self, missing/unaccepted/unverified/removed contacts and projected denial. Unrelated safe contacts remain usable. [`state.tsx`](../../apps/mobile/src/state.tsx) synchronously updates the current block reference; final send passes that current policy into the required fifth [`createMessage()`](../../apps/mobile/src/model.ts) argument. Contact approval/reverification does not delete independent edges. Final schedule save rechecks the same policy. Composer/review/contact eligibility and [`isRecipientAllowed()`](../../apps/mobile/src/journal-intelligence/index.ts) honor messagingBlocked, while safety information and separate in-person preparation remain accessible.

Six domain tests, three added factory tests and one journal test cover both directions, stale verified references, parent base approval/reverification, independent ownership, unrelated contacts, self/connection gates, immutable projection and rejected explicit model recipients. The integrated targeted suites passed **21 tests**. R12's complete gate then passed **84 unit tests and 19 browser scenarios**, including both actual-control cases in [`e2e/blocking.spec.ts`](../../apps/mobile/e2e/blocking.spec.ts): reverse-account composer/review denial while safety/in-person practice remain usable. TypeScript/lint, audit, Doctor, compatibility and both exports also passed. The master obtained independent read-only approval of the connected source, including schedule gating. No new unblock feature was added.

The [focused native QA report](../qa/chores-goals/1116-r12-bidirectional-blocks/QA_REPORT.md) closes this defect for build r12/source `8607573e37dadd66ede3bb368389e0a2531ef6d8`: four actual block cases passed across child/parent ownership and Safe Harbor/Night Harbor, with disabled composer/Review and new-schedule Save, while each child safety/other-adult practice flow succeeded. Appearance persistence passed after process restart, and original geometry/font properties were restored without errors. The manifest is completed/error-null; all 14 original Android PNGs were individually inspected and independently SHA-256/IHDR verified by the evidence reviewer. The unavailable copy does not expose the private block owner's identity/reason.

This native evidence covers the visible control denials and safe preparation paths, not an internal forced send or a block arriving between Review and Send. Current-reference/factory branches have separate source/unit coverage. It does not establish production identities, queued delivery revocation or authenticated server permissions, and it does not close the separate opaque-ID current-build evidence requirement.

## Other reviewed boundaries

Apart from the two findings documented above, no additional blocking regression was found in the following connected implementation paths:

- **Financial projections and commands:** [`finance/engine.ts`](../../apps/mobile/src/finance/engine.ts) enforces parent operations and child ownership independently of buttons. It rejects unknown command fields, freezes/copies ledger inputs, and projects child DTOs without raw matching configuration or hidden effects. Hidden funding leaves the child projection unchanged until reveal; allocation decisions use the child's own balance rather than hidden promises. The sequential-reference finding above remains an exception until corrected.
- **Financial UI:** [`finance-state.tsx`](../../apps/mobile/src/finance-state.tsx) exposes the projection and guarded command runner rather than the raw ledger. [`Finance.tsx`](../../apps/mobile/src/screens/Finance.tsx) gates parent management and labels payment records as declarations. Provider handoffs use explicit parent clipboard/open-link actions; no provider balance lookup or money-transfer API was found in these callers.
- **Author separation and final send:** [`state.tsx`](../../apps/mobile/src/state.tsx) reads/writes journals by the selected author, clears unsent editor/recipient state on confirmed role change, and rechecks recipient restrictions at send. [`model.ts`](../../apps/mobile/src/model.ts) rejects blocked, unaccepted or unverified recipients. [`Messaging.tsx`](../../apps/mobile/src/screens/Messaging.tsx) presents a separate editable draft and explicit review/send; in-person preparation does not send. These are prototype UI/domain boundaries, not secure login authorization.
- **Journal assistance:** [`Journal.tsx`](../../apps/mobile/src/screens/Journal.tsx) keeps automatic assistance opt-in per role, cancels stale/background work and requires explicit recipient selection and separate message review. [`journal-intelligence/index.ts`](../../apps/mobile/src/journal-intelligence/index.ts) validates bounded output and excludes unsafe people. Actual fixture probes for `Alex hurt me today.`, `Alex is unsafe.` and `My dad hurt me today.` all excluded the seeded `Alex - parent`; first-name aliases were already covered by the current implementation.
- **Model and storage boundary:** [`local-model.native.ts`](../../apps/mobile/src/local-model.native.ts) downloads a constant pinned public model asset only after explicit action, checks size/SHA-256 before load and suppresses native logs. [`local-model-contract.ts`](../../apps/mobile/src/local-model-contract.ts) serializes generation, cancels stale requests, requests native cache cleanup before/after prompts and retires a context after cleanup failure. It exposes no session persistence APIs. Source inspection found appearance storage and model assets, plus the explicit parent payout clipboard action; no journal/finance network transport, analytics, content-file persistence or app console logging was found in these reviewed paths. Network capture and independent native-binary audit were not performed.
