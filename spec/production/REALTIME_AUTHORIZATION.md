## Surface and authority

The only published application table remains `api.user_invalidations(id,user_id)`: opaque own-user refresh hints, no message/finance/report/journal/question/skip content or domain identifiers. A hint is not proof of delivery, a read receipt or permission to fetch a body. Every actual content fetch still rechecks its own session, current family/contact/consent/block/object rules. The mobile client filters INSERTs to its own UID, and treats them only as prompts for fresh authorized fetches.

The original RLS policy matched `user_id=auth.uid()` alone. A cryptographically valid but revoked/expired/withdrawn identity could therefore still satisfy the row comparison. Migration 017 replaces that policy with `api.can_read_own_invalidation(user_id)`.

`can_read_own_invalidation(p_user_id uuid) -> boolean` is a narrowly exposed authenticated-only SECURITY DEFINER function with empty pinned search path. It returns true only when the argument equals the caller's managed UID, signed JWT role is `authenticated`, JWT expiry is present and later than the actual server clock, ordinary `app_private.actor()` validates the existing managed session/account, and `account_usable()` confirms current active product authority. This excludes actor's limited onboarding allowance, a withdrawn child, suspended/closed/banned/unverified/deleted accounts, expired/removed/other-user sessions and malformed/missing claims. It catches authorization errors and returns false. It exposes no underlying reason, identity existence, metadata or arbitrary lookup result for other users.

Only the boolean API function gets an authenticated execution grant. No private-schema usage, private table access or private helper execution is granted. Authenticated SELECT on the opaque hint table remains governed by RLS; INSERT/UPDATE/DELETE remain server-only. Anonymous users cannot call the boolean or read hints even when a SQL test fixture supplies forged claims. Client role metadata is ignored. There is no custom JWT decoder, issuer, signature implementation or historical-privacy-identity fallback. Signature/issuer/audience enforcement at the actual Auth/PostgREST/Realtime boundary remains a release qualification; the SQL function consumes that trusted request context.

The helper is volatile because the existing actor takes a SHARE lock on its managed session, serializing with session deletion. It requires a database authorization context capable of that check; a read-only/incompatible evaluation suppresses hints instead of weakening authorization. This migration does not grant access to `auth.sessions`. Use the normal authorized RPC polling path when hints are unavailable; do not replace the check with UID equality.

## Postgres Changes compatibility and DELETE protection

Supabase documents per-event, per-subscriber authorization for Postgres Changes and warns that DELETE events do not apply RLS. Therefore client INSERT filters alone cannot constrain a hostile wildcard subscriber. The publication must exclude deletion events at the server. [Official Postgres Changes documentation](https://supabase.com/docs/guides/realtime/postgres-changes).

Under the owner's approved hints-only architecture, 017 requires `supabase_realtime` to exist, not publish all tables, and contain **exactly** `api.user_invalidations`. Missing or additional tables abort with `55000 / invalidation publication requires explicit review`; the migration never silently removes another domain or broadens publication. It then sets publication actions to INSERT only and verifies `pubinsert=true`, `pubupdate=false`, `pubdelete=false`, `pubtruncate=false`. Retention/privacy cleanup may still delete database hint rows, but those deletions are not published. UPDATE/TRUNCATE are excluded as well. Existing 002 source stays unchanged; fresh installs must apply the complete ordered migration set before any access.

The official WALRUS implementation used by the Postgres Changes pipeline stores subscription claims and, for each non-DELETE RLS check, sets the subscription's database role and full `request.jwt.claims` before querying the row. That supports `auth.uid()`, JWT `exp` and managed `session_id` consumption without granting clients private schema access. It also explicitly bypasses RLS in the DELETE branch, confirming why publication filtering is needed. This is upstream-source evidence, not proof that every installed/hosted Realtime version has identical behavior. [Official Supabase WALRUS implementation](https://github.com/supabase/walrus/blob/master/sql/walrus_migration_0016_fix_apply_rls_role_leak.sql), [official pipeline explanation](https://github.com/supabase/walrus#how-it-works).

Do not confuse this mechanism with Broadcast/Presence authorization on `realtime.messages`. Supabase describes that separate channel access cache as updating on subscription or a new JWT. No Broadcast/Presence policy is introduced here and those cache semantics must not be used to claim database session revocation checks are unnecessary. [Official Realtime Authorization documentation](https://supabase.com/docs/guides/realtime/authorization). The client SDK's token update behavior also needs testing on refresh/reconnect; supplying or parsing a token locally does not establish server permission. [Official `setAuth` reference](https://supabase.com/docs/reference/javascript/setauth).

## Hint retention correction — migration 020 source

`202611160020_invalidation_retention.sql.pending` fixes the original `invalidate_user` algorithm without editing applied 002. Sorting random UUIDs and retaining the lowest twenty did not retain the newest hint: once full, an inserted high UUID could be deleted immediately, leaving WALRUS no live row to authorize. This was independently identified while diagnosing Realtime; it did not cause the small initial bootstrap fixtures above.

The API table and publication retain exactly `{id,user_id}`. New `app_private.invalidation_creation` records the hint FK, owner and a generated-always identity ordinal. An AFTER INSERT trigger registers every server hint, then prunes using the private ordinal. No event timestamp, sequence, ordinal, source kind or ordering table is exposed in API/RLS/Realtime or author exports. No new actor-dependent financial emission is added; parent-only activity cannot expose global ordinal gaps through a child DTO. Authenticated/anonymous/service clients receive no private table, sequence or helper grant. Hint identity/owner updates are rejected so public ownership cannot diverge from metadata.

Private rows reference the public hint ID with `ON DELETE CASCADE`; existing prune, privacy erasure and Auth-user cascade paths therefore remove associated ordering metadata. It is disposable transport metadata, not evidence or a message archive. Root must apply this migration atomically/serially with **explicit `BEGIN` / `COMMIT` in the migration file**: actual Supabase CLI 3.1.0 application did not supply a transaction and the initial `LOCK TABLE` failed with `25P01` at statement zero before any 020 object was created. Root owns adding the transaction wrapper to the unapplied source before retry. Its writer lock then prevents registration/backfill races. Do not infer transaction wrapping for future migrations from CLI execution alone. Legacy hint creation times were not recorded; backfill explicitly assigns an unknown relative order to old retained rows, all before subsequent inserts. It never fabricates historical event times or claims to recover hints previously pruned by UUID sorting.

Concurrency choice is deliberate: retention calls `pg_try_advisory_xact_lock` per owner and **does not wait**. Existing domain operations already hold family/pair locks and can invalidate multiple authors in different orders. Introducing blocking per-author locks there could create cycles; this patch preserves those domain lock/authorization guards. A successful uncontended emission retains exactly its newest twenty rows. If another transaction holds that hint-retention lock, the new row/ordinal is retained and pruning is deferred. Concurrent commits may temporarily exceed twenty; a later successful emit repairs that owner's overflow. No strict concurrent cap, background repair timer or unattended maintenance deployment is claimed. An idle overflow can remain until a later successful emit or approved owner maintenance; concurrency/resource qualification remains a release gate.

Hints are coalescible refresh prompts. Even correct retention can prune an older hint after twenty newer emissions before a subscriber checks it; the system does not promise one delivered hint for every change. Actual messages/financial commands remain persisted under their own authorization/idempotency rules, and clients keep their authorized polling/retry path. A hint never permits an otherwise forbidden body fetch.
